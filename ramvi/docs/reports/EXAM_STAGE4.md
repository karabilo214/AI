# Этап 4 на железе: контрольный прогон (4.7), экзамены 2, 3, 5 ТЗ (4.9), A/B движка 4.10

Дата: 2026-11-17. Ноутбук: RTX 5060 Laptop 8 ГБ (драйвер 616.92), Ryzen 7 260 (8 ядер / 16 потоков),
16 ГБ RAM, Windows 11. Комплект RAMVI с текущим кодом, отдельный экземпляр сервиса со своей папкой
данных; модели — файлы Ollama (подключены на месте) и скачанные из каталога. Данные пользователя не
затрагивались.

## 4.7 — контрольный прогон

Прогрев + 3 запроса по 64 токена (2 коротких «текст на ~100 слов» и 1 длинный ≈ половина контекста),
контекст 2048, автоугадыватель сервиса включён, как в чате.

| Модель | Оценка до прогона, ток/с | Прогон, ток/с | Время до 1-го токена | Пик VRAM / RAM | Слои | Стабильно |
|---|---|---|---|---|---|---|
| qwen3 0.6B Q4_K_M | 230–270 | 231–379 | 0,05 с | 0,7 / 1,5 ГБ | 28 GPU | да |
| qwen3 8B Q4_K_M | 48–57 | 6,6–30,9 | 0,27 с | 5,7 / 6,1 ГБ | 36 GPU | да |
| qwen3 14B Q4_K_M | 7,8–9,1 (замер WIDE30) | 3,5–5,3 | 0,58 с | 6,1 / 9,1 ГБ | 20 GPU / 9 шина / 11 гибрид | да |

Результат сохранён и виден в каталоге/списке моделей как «замер на этом ПК» с фактическими
ресурсами (карточка экрана «Модели», 4.11).

Найдено прогоном (для движка, не исправлялось — правка движка требует отдельного экзамена скорости):

1. **8B целиком в VRAM с автоугадывателем в 1,5–2 раза медленнее**, чем без него (без угадывателя
   этот же движок даёт 39–42 ток/с — A/B ниже). Это та же нераскрытая разница «32,8 у RAMVI против
   52,2 у Ollama» из прошлых заметок: для модели, целиком лежащей в видеопамяти, угадыватель мешает.
2. **14B на творческих запросах 3,5–5,3 ток/с** против 7,8–9,1 в WIDE30: угадыватель плохо угадывает
   творческий текст (в WIDE30 «творчество» тоже было самым медленным).
3. **Длинный запрос (~1500 токенов) читается медленно:** 15,8 с у 8B и 30 с у 14B. WIDE30 таких
   запросов не содержал.

Исправлено по ходу: page faults считались у процесса-привратника движка (0) — теперь по всему
дереву процессов; запросы прогона заменены на «текст ~100 слов» (короткие ответы давали 11–27 токенов).

## Экзамен 5 ТЗ — обрыв скачивания — пройден (с оговоркой о способе)

`qwen3:0.6b` (522 МБ) из реестра Ollama:

1. **«Выключение питания»** — процесс сервиса убит на 151 МБ. После запуска: загрузка на паузе,
   `.part` 159 МБ, модель не подключена.
2. **Нет сети** — сервис запущен с недоступным прокси: продолжение → автоповторы → пауза с причиной
   `download.interrupted`, частичный файл цел.
3. **Сеть вернулась** — продолжение, загрузка до конца, SHA-256 файла совпал с каталогом
   (`7f403014…`), модель подключена.
4. **Повреждённые данные** — на паузе в `.part` записан 1 МБ мусора: после продолжения
   `download.hash_mismatch`, файл удалён, модель не подключена.

Оговорка: оборвать уже идущее соединение правилом брандмауэра Windows не удалось (правило не
задерживало соединения Python на этой машине), а отключать сетевой адаптер нельзя — оборвётся
управление машиной. Поэтому «сеть пропала» — это закрытие соединения (выход процесса) и недоступный
прокси при новом соединении. Обрыв посреди потока проверяется тестом с сервером, рвущим соединение
(`tests/test_download_manager.py`), продолжение по Range после переадресации на CDN проверено в 4.3.

## Экзамен 3 ТЗ — смена оборудования — пройден (с оговоркой)

Папка приложения с данными и скачанной моделью (`qwen3:1.7b`, относительный путь) перенесена с
ноутбука на Mac M1 Pro без NVIDIA:

- чаты и сообщения на месте (вопрос и ответ `3973`);
- модель внутри переносимой папки найдена, её статус пересчитан под этот компьютер («Не
  поддерживается: нужна NVIDIA»), замер контрольного прогона с ноутбука не применён (другой
  отпечаток железа);
- рекомендации пересчитаны: запускаемых моделей нет, причины перечислены.

Оговорка: модели, подключённые на месте из папки Ollama ноутбука (абсолютные пути Windows), на Mac
показаны как «Нет данных» — их файлов здесь нет. Понятнее был бы отдельный статус «файл модели не
найден» (бэклог B.5).
