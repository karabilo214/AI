### На ноутбуке с RTX 5060, настоящие модели (2026-11-19)

Скрипт `stage8_checks/exam4_offline.py`, результаты — `stage8_checks/exam4_results.json`. Прав администратора на правило брандмауэра нет, поэтому сеть отрезана ловушкой во **всех процессах Python комплекта** (`stage8_checks/offline_guard_sitecustomize.py`). Ловушка кладётся на время проверки как `sitecustomize.py` и отклоняет любое соединение и DNS-запрос не к 127.0.0.1. Ловушку загрузили 5 процессов: скрипт, движок и его загрузчик, распознаватель речи и его загрузчик. Окружение как у оболочки (`HF_HUB_OFFLINE`, `TRANSFORMERS_OFFLINE`, `PYTHONNOUSERSITE`). Контроль: запросы к huggingface.co и 192.0.2.1 отклонены.

| Проверка | Результат |
|---|---|
| Чат, qwen3:8b Q4_K_M, «Сколько будет 17*23?» | «391», 21,6–40,4 с с загрузкой модели (4 запуска) |
| Голос, whisper large-v3-turbo q5_0 на CPU, 3 русские записи FLEURS (13,7 / 7,4 / 11,8 с) | слов совпало 26/26, 8/9 («WiFi» → «Wi-Fi»), 18/20 («7-м» → «седьмым», скобки) |
| Файлы агента: чтение, поиск, правка с diff, применение | всё работает |
| Попытки выйти в сеть, кроме контрольных | **0** |

После проверки ловушка удалена из комплекта, процессов не осталось, видеопамять 0 MiB.

**Находка о памяти — разобрана и исправлена.** С загруженной qwen3:8b процесс движка держал 5,7 ГБ RAM, «доступно» оставалось около 300–440 МБ, и голос отказывал (`voice.no_memory`). Замер (`stage8_checks/engine_memory_probe.ps1`, модель целиком в видеокарте, 36 слоёв, закреплённой RAM 0):

| | рабочий набор | из них частные | из них страницы файла | «доступно» в системе |
|---|---|---|---|---|
| до исправления, после загрузки | 5 728 МБ | 908 | **4 820** | 440 МБ |
| то же, после принудительного сжатия рабочего набора | 140 | 1 | 139 | 5 507 МБ |
| **после исправления**, после загрузки | **1 086 МБ** | 909 | 177 | **5 030 МБ** |

Это не копия весов: движок читает файл модели через memmap и переливает веса в видеокарту, а прочитанные страницы файла оставались в его рабочем наборе. Windows не считает такие страницы «доступной» памятью. Исправление (`formats/gguf.py: release_file_pages`, вызов в конце загрузки `GGUFEngine`): страницы выводятся из рабочего набора (Windows — `VirtualUnlock`, POSIX — `madvise`), отображение файла остаётся. Если страница понадобится слою на процессоре, система подчитает её из кэша. Экзамен 4 повторён **без выгрузки модели**: свободно 5 005 МБ, движок 1 107 МБ; чат «391», голос 26/26, 8/9, 18/20, файлы агента работают, попыток выйти в сеть 0. Частная выделенная память (commit) движка 7,4 ГБ — это резерв под видеопамять и библиотеки CUDA. Он почти весь не в RAM (частных страниц в рабочем наборе 0,9 ГБ) и расходует лимит подкачки, а не RAM.

**Память свободного ноутбука** (16 ГБ, системе видно 15,6 ГБ: 0,7 ГБ отдано встроенной графике Radeon 780M). Без RAMVI занято около 9,8 ГБ, «доступно» 5,9 ГБ (из них 5,1 ГБ — кэш файлов, его система отдаёт по требованию). Крупнее всего: Wargaming Game Center — 3,5 ГБ (5 процессов `wgc_renderer_host`, запущен накануне в 23:30), `vmmemCmZygote` — 0,84 ГБ (остаток Windows Sandbox после проверки 8.1, уйдёт после перезагрузки, когда отключение компонента завершится), невыгружаемый пул ядра — 0,84 ГБ, Discord — 0,55 ГБ, Защитник Windows — 0,46 ГБ, 83 службы svchost — 0,39 ГБ.

## Экзамен 10: сбои без повреждения данных

`tests/test_exam10_failures.py`. После каждого сбоя проверяется: `PRAGMA integrity_check` = ok, прежняя история на месте, следующий запрос работает.

| Сбой | Что видит пользователь | Проверка |
|---|---|---|
| Нехватка памяти при загрузке модели | `engine.no_memory` | тест экзамена 10; также `test_ui_states.py` |
| Повреждённая модель | `engine.start_failed` после повторов | тест экзамена 10 |
| Падение движка посреди ответа | ответ помечен ошибкой, полученная часть сохранена, движок перезапускается, следующий ответ работает | тест экзамена 10 (`CRASH_MID` в тестовом движке) |
| Полный диск | `storage.disk_full`: «Нет места… прежние данные целы», папка для освобождения места; HTTP 507 | 3 теста: сообщение пользователя, сохранение ответа, откат транзакции целиком |
| Обрыв клиента посреди потока | генерация останавливается, сервис продолжает работать | тест экзамена 10; также `test_chat.py` |
| Драйвер недоступен | проверка компьютера называет нужную версию драйвера | `test_onboarding.py` (8.1) |
| Ошибки распознавания речи | понятные коды, состояние возвращается в «готов» | `test_voice.py` |

**Найдено и исправлено:** при полном диске пользователь получал «внутреннюю ошибку» с текстом «cannot rollback - no transaction is active». SQLite сам откатывает транзакцию при `SQLITE_FULL`, а наш повторный откат падал и прятал настоящую причину. Теперь `Database` откатывает только активную транзакцию, переводит `SQLITE_FULL` в `DiskFull`, а сервис показывает `storage.disk_full`. Если диск полон при сохранении ответа, ответ завершается этой ошибкой, а не обрывом потока.
