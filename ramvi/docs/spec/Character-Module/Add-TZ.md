

# RAMVI — Character Module


## Дополнение и исправление архитектурных требований ТЗ

### 1. Назначение RAMVI

**RAMVI сохраняет своё первоначальное назначение, архитектуру и функциональность.**

Разработка системы эмоциональных ИИ-персонажей не предполагает изменения концепции RAMVI или превращения приложения в специализированного голосового ассистента.

Новая функциональность реализуется как **самостоятельный модуль Character**, аналогично существующим модулям Chat и Agent.

### 2. Архитектура платформы

```text
                         RAMVI
                           |
                    RAMVI Core
                           |
          +----------------+----------------+
          |                |                |
         Chat             Agent          Character
          |                |                |
          +----------------+----------------+
                           |
                   Shared Services
                           |
               LLM Provider Abstraction
               Configuration / Settings
               Storage / Persistence
               Resource Management
               Event Infrastructure
```

*Схема логическая: перечень общих сервисов необходимо сопоставить с фактической архитектурой текущего RAMVI. Она не предполагает обязательного создания новых подсистем в ядре.*

### 3. Модуль Character

Модуль Character реализует функциональность, описанную в предыдущем ТЗ:

- Personality Engine — базовый характер персонажа.
- Emotional State Engine — эмоциональные состояния.
- Memory Engine — долговременная память.
- Behavioral Adaptation Engine — адаптация поведения.
- Voice Engine — распознавание и синтез речи.
- Animation Engine — визуальное представление персонажа.
- Context Orchestrator — подготовка контекста.
- Response Planner — формирование сценария эмоционального ответа.

Все эти подсистемы принадлежат **модулю Character**, а не RAMVI Core.

### 4. Требования к модульности

1. **Независимость.** Character должен запускаться, отключаться и обновляться независимо от Chat и Agent.

2. **Отсутствие регрессий.** Добавление Character не должно изменять существующую логику Chat, Agent, подключения моделей и управления ресурсами.

3. **Повторное использование сервисов.** Character должен использовать существующие интерфейсы RAMVI для LLM, конфигурации и хранения данных там, где они подходят.

4. **Изоляция данных.** Профили персонажей, их состояния, память и настройки должны храниться в собственном пространстве данных модуля.

5. **Изоляция ресурсов.** При отключённом Character его аудиосистема, анимационный движок и фоновые задачи не должны потреблять ресурсы.

6. **Независимость интерфейса.** Пользователь может работать исключительно с Chat или Agent, вообще не используя Character.

7. **Расширяемость.** Архитектура Character должна допускать подключение новых TTS, STT, LLM, персонажей и анимационных движков без переработки RAMVI Core.

8. **Необязательность human_brain.** Интеграция human_brain должна выполняться только через экспериментальный адаптер внутри Character.

### 5. Взаимодействие с Agent

Character может использовать функциональность Agent, но не заменяет её.

Пример:

Пользователь голосом просит персонажа проанализировать проект.

Character распознаёт речь и определяет запрос. Через публичный интерфейс RAMVI передаёт задачу модулю Agent. Agent выполняет работу и возвращает результат. Character озвучивает его с учётом выбранного характера.

При этом:

- Character не дублирует агентный движок.
- Agent не зависит от Character.
- Права доступа и подтверждения действий остаются под контролем Agent и RAMVI.
- Обычный текстовый вызов Agent продолжает работать без Character.

### 6. Жизненный цикл

Character должен поддерживать независимые операции:

```text
initialize()
activate()
deactivate()
suspend()
resume()
dispose()
```

При деактивации:

- Останавливается захват аудио.
- Прекращается синтез речи.
- Отменяются активные анимации.
- Освобождаются занятые ресурсы.
- Сохраняется необходимое состояние персонажа.
- Chat и Agent продолжают работать без изменений.

### 7. Ограничения разработки

**Запрещается:**

- Переносить специфическую логику персонажа в RAMVI Core.
- Делать Character обязательным компонентом запуска.
- Привязывать Chat или Agent к Emotional State Engine.
- Изменять существующие интерфейсы без подтверждённой необходимости.
- Дублировать в Character существующие общие механизмы RAMVI.
- Создавать прямые зависимости Agent → Character или Chat → Character.

Если для реализации Character требуется новая общая возможность платформы, она должна оформляться как минимальное расширение существующего публичного интерфейса RAMVI, без изменения поведения других модулей.

### 8. Критерии приёмки модульности

Разработка считается соответствующей архитектуре, если:

1. RAMVI запускается и работает без установленного или активированного Character.
2. Chat и Agent сохраняют существующее поведение.
3. Character может использовать подключённые через RAMVI модели.
4. Отключение Character освобождает связанные ресурсы.
5. Обновление Character не требует переработки Chat или Agent.
6. Character может вызвать Agent только через предусмотренный интерфейс.
7. Удаление Character не приводит к потере данных других модулей.
8. Тесты существующих компонентов RAMVI проходят без регрессий.

### 9. Архитектурное правило

**RAMVI — платформа. Chat, Agent и Character — независимые функциональные модули.**

Character расширяет возможности RAMVI, но не меняет его назначение.

Все требования предыдущего ТЗ, относящиеся к эмоциональному поведению, памяти, голосу, анимации и адаптации, должны реализовываться внутри Character либо через существующие общие сервисы платформы.
