# RAMVI — Character, Voice & Memory Engine
## Техническое задание на разработку интеллектуального персонажа

**Версия:** 1.0  
**Статус:** Проектное ТЗ  
**Назначение:** Реализация голосового ИИ-персонажа с эмоциональным поведением, анимацией, долговременной памятью и адаптивным характером в экосистеме RAMVI.

---

# 1. Цель проекта

Разработать модульную систему взаимодействия с LLM, в которой пользователь общается не с обычным текстовым чат-ботом, а с виртуальным персонажем, имеющим:

- Индивидуальный, узнаваемый характер.
- Естественную эмоционально окрашенную речь.
- Анимированное лицо, синхронизированное с голосом.
- Способность понимать контекст, юмор, иронию и словесные подвохи.
- Долговременную память о разговорах и пользователе.
- Устойчивые особенности поведения.
- Способность адаптироваться на основании накопленного опыта.
- Возможность проявлять инициативу, не ограничиваясь буквальным исполнением запросов.

**Основной принцип:** LLM отвечает за языковые и интеллектуальные операции, RAMVI — за память, характер, состояние персонажа, управление взаимодействием и подключение внешних систем.

Система не должна зависеть от конкретной LLM, поставщика синтеза речи или движка анимации.

# 2. Границы реализации

## 2.1. Обязательные возможности

В первой полноценной версии должны работать:

1. Двусторонний голосовой диалог.
2. Потоковое воспроизведение эмоциональной речи.
3. Выбор персонажа и его характера.
4. Синхронизация анимации с голосом.
5. Постоянное состояние персонажа между репликами.
6. Долговременная память между сессиями.
7. Извлечение релевантных воспоминаний.
8. Адаптация поведения на основании опыта.
9. Распознавание юмора, провокаций и двусмысленностей.
10. Контекстная генерация ответных шуток.
11. Подключение различных LLM.
12. Локальное хранение профилей и памяти с управлением со стороны пользователя.

## 2.2. Что не требуется для первой версии

- Создание собственной большой языковой модели.
- Обучение LLM с изменением её весов.
- Полноценная 3D-анимация.
- Обязательное подключение human_brain.
- Распознавание настоящих человеческих эмоций со стопроцентной точностью.
- Самостоятельное изменение программного кода персонажем.

Эти функции не должны блокировать разработку базовой архитектуры.

# 3. Общая архитектура

```text
                 USER
                   |
          Microphone / Text
                   |
             Input Engine
            STT / VAD / Audio
                   |
           Conversation Engine
                   |
          Context Orchestrator
             /      |      \
            /       |       \
       Memory    Personality  State
       Engine      Engine    Manager
            \       |       /
             \      |      /
                LLM API
                   |
           Structured Response
                   |
            Response Planner
                /       \
               /         \
          Voice Engine  Animation Engine
               \         /
                \       /
             Sync Controller
                   |

```

Управление должно быть событийным.

Состояния не должны передаваться исключительно последовательными синхронными вызовами.

Каждый компонент должен иметь собственный интерфейс, чтобы его можно было заменить без изменения остальных модулей.

# 4. Personality Engine — система характера

## 4.1. Базовый характер

При создании персонажа пользователь выбирает один из базовых профилей:

| Профиль | Характеристика |
|---|---|
| Neutral | Спокойный, рациональный |
| Friendly | Дружелюбный, поддерживающий |
| Sarcastic | Ироничный, остроумный |
| Strict | Строгий, требовательный |
| Curious | Любознательный, инициативный |

Должна поддерживаться возможность создания пользовательских профилей.

## 4.2. Параметры характера

Каждый профиль содержит устойчивые черты:

```json
{
  "id": "sarcastic",
  "traits": {
    "humor": 0.9,
    "sarcasm": 0.85,
    "curiosity": 0.7,
    "initiative": 0.65,
    "emotionality": 0.8,
    "assertiveness": 0.7
  },
  "adaptation": {
    "enabled": true,
    "learning_rate": 0.05
  }
}
```

Параметры имеют диапазон 0–1.

Базовые черты не должны автоматически перезаписываться каждой пользовательской репликой.

## 4.3. Устойчивость характера

**Ключевое требование:** персонаж должен сохранять узнаваемую индивидуальность на протяжении длительного общения.

Пример:

**Человек:** «Так, всё, давай серьёзно!»

**Ассистент:** «Конечно, только шнурки завяжу!»

Такой ответ допустим в ситуации непринуждённого общения, когда пользователь поддерживает шутливый стиль.

При этом устойчивость характера не должна означать игнорирование явно установленных границ. При серьёзной просьбе прекратить подколы ассистент обязан изменить манеру ответа, сохраняя другие узнаваемые особенности личности.

Необходимо различать:

- Базовые черты характера.
- Временное эмоциональное состояние.
- Настройки пользователя.
- Явные ограничения общения.
- Приобретённые предпочтения.

Приоритет явных ограничений выше предпочтений и адаптивных параметров характера.

# 5. Emotional State Engine — эмоциональные состояния

## 5.1. Назначение

Поддерживать внутреннее состояние персонажа, влияющее на:

- Выбор слов и построение ответа.
- Интонацию.
- Скорость речи.
- Громкость.
- Анимацию лица.
- Вероятность инициативной реакции.

Состояние является вычислительной моделью эмоций, а не утверждением о наличии субъективных переживаний у ИИ.

## 5.2. Базовые состояния

Минимальный набор:

```text
neutral
happy
amused
curious
surprised
confused
annoyed
indignant
sad
sarcastic
```

Архитектура должна позволять добавлять состояния без изменения ядра.

## 5.3. Интенсивность

Каждое состояние имеет интенсивность от 0 до 1.

Пример:

```json
{
  "primary": "indignant",
  "intensity": 0.85,
  "secondary": "surprised",
  "secondary_intensity": 0.45
}
```

Первичные и вторичные состояния могут сосуществовать.

## 5.4. Жизненный цикл состояния

Эмоциональное состояние не должно полностью обнуляться после каждой реплики.

Требуется реализовать:

- Изменение состояния после событий.
- Плавное ослабление временных реакций.
- Переключение при новых обстоятельствах.
- Сохранение значимого состояния между соседними репликами.
- Отдельный режим восстановления нейтрального состояния.

Например:

```text
neutral
  ↓
surprised
  ↓
indignant
  ↓
sarcastic
  ↓
amused
  ↓
neutral
```

Переходы определяются контекстом, базовым характером и результатами предыдущих взаимодействий.

Запрещается жёстко закреплять правило, по которому любой конкретный текст всегда вызывает одну и ту же эмоцию.

# 6. Understanding & Humor Engine

## 6.1. Назначение

Обеспечить распознавание:

- Шуток.
- Иронии.
- Сарказма.
- Двусмысленных формулировок.
- Словесных ловушек.
- Фонетических созвучий.
- Межъязыковых каламбуров.
- Провокаций.
- Намеренного изменения темы.
- Социального подтекста разговора.

## 6.2. Генерация реакции

Модель должна учитывать:

1. Буквальное содержание сообщения.
2. Предполагаемый коммуникативный смысл.
3. Контекст предыдущих реплик.
4. Релевантные воспоминания.
5. Характер персонажа.
6. Текущее эмоциональное состояние.
7. Основную цель разговора.

Реакция не должна всегда быть шутливой.

Персонаж самостоятельно выбирает наиболее уместный тип ответа в пределах установленных правил.

## 6.3. Проверочный сценарий

**Пользователь:** «Как проще сказать "да" по-английски?»

**Ассистент:** «Yeah».

**Пользователь:** «А день?»

**Ассистент:** «Day».

**Пользователь:** «А счёт в ресторане?»

**Ассистент:** «Bill».

**Пользователь:** «Теперь соедини все три слова».

Ожидаемые способности:

- Распознать возможность фонетического подвоха.
- Учесть русский и английский языки.
- Выбрать уместную реакцию.
- При необходимости изобразить удивление.
- Создать эмоционально выразительный ответ.
- Согласовать голос с анимацией.
- При сохранении учебной цели вернуться к занятию.

Нельзя жёстко прописывать ответ для этой конкретной последовательности. Она используется только как контрольный тест.

# 7. Voice Engine — голосовая система

## 7.1. Входящий звук

Реализовать постоянную обработку микрофона во время активного голосового сеанса.

Требования:

- Voice Activity Detection (VAD).
- Распознавание речи.
- Поддержка русского и английского языков.
- Обработка переключения языка в пределах одной реплики.
- Обнаружение начала и окончания речи.
- Поддержка перебивания ассистента.
- Подавление эха собственного синтезированного голоса.
- Прерывание текущего ответа при необходимости.

Слово «постоянная» означает обработку в рамках явно активированной голосовой сессии, а не скрытое прослушивание.

## 7.2. Выходящий звук

Реализовать абстракцию TTS-провайдера.

Первые кандидаты:

- Google Gemini-TTS.
- ElevenLabs.
- OpenAI Speech / Realtime.

Ни один поставщик не должен быть жёстко встроен в бизнес-логику.

## 7.3. Эмоциональная озвучка

TTS должен получать:

```json
{
  "text": "Это ты сейчас серьёзно?!",
  "emotion": "indignant",
  "intensity": 0.85,
  "style": "expressive conversational Russian"
}
```

Адаптер преобразует эти данные в формат конкретного поставщика.

Если поставщик не поддерживает эмоциональные настройки, система использует ближайший доступный режим, не выдавая его за точное воспроизведение запрошенной эмоции.

## 7.4. Требования к естественности

Голос должен по возможности обеспечивать:

- Естественное русское произношение.
- Правильные ударения.
- Выразительную интонацию.
- Смысловые паузы.
- Изменение эмоциональности внутри ответа.
- Разговорный темп.
- Корректное произношение англоязычных вставок.
- Отсутствие заметной роботизированной монотонности.

Качество оценивать отдельными тестами на русском языке, а не только по демонстрациям поставщиков.

# 8. Animation Engine — анимированный персонаж

## 8.1. Формат

Для первой версии использовать 2D-персонажа.

Поддерживать:

- Мимику.
- Движения глаз.
- Моргание.
- Движение рта.
- Повороты и наклоны.
- Эмоциональные переходы.
- Idle-анимации.
- Дополнительные эффекты (цвет, свечение, пламя и др.).

Рекомендуется отделить описание персонажа от анимационного движка.

## 8.2. Синхронизация с голосом

Одна и та же информация об эмоциональном состоянии должна поступать в Voice Engine и Animation Engine.

Нельзя реализовывать два независимых механизма, которые отдельно угадывают нужную эмоцию.

При доступности речевых таймкодов использовать их для привязки движения рта и эмоциональных переходов.

При отсутствии таймкодов допускается приближённая синхронизация по амплитуде аудио, с возможностью последующей замены на фонемный или виземный анализ.

## 8.3. Требования к производительности

- Отрисовка персонажа с целевой частотой 60 FPS.
- Возможность работы на CPU без выделенного GPU.
- Анимация не должна блокировать голос или LLM.
- Задержки генерации речи не должны замораживать персонажа.
- При отмене ответа соответствующие анимационные события должны отменяться.
- Idle-анимации должны продолжаться между репликами.

# 9. Structured Response Protocol

LLM должна возвращать не только текст, но и структурированный сценарий ответа.

Пример внутреннего контракта:

```json
{
  "intent": "playful_retort",
  "emotion": {
    "primary": "amused",
    "intensity": 0.75
  },
  "segments": [
    {
      "text": "Подожди...",
      "emotion": "surprised",
      "intensity": 0.6,
      "voice_style": "confused",
      "animation": "surprised"
    },
    {
      "text": "Это ты сейчас меня подловить решила?!",
      "emotion": "indignant",
      "intensity": 0.9,
      "voice_style": "mock_indignation",
      "animation": "angry"
    }
  ],
  "memory_candidates": []
}
```

Требования:

- Валидация по JSON Schema.
- Перечисления допустимых эмоций и анимаций.
- Ограничения длины полей.
- Корректная обработка частичного вывода.
- Безопасный fallback на обычный текст.
- Разделение пользовательского текста и управляющих инструкций.
- Отмена очереди сегментов при перебивании.
- Поддержка потоковой генерации.

Для уменьшения задержки протокол должен позволять получать и воспроизводить завершённые сегменты до генерации всего ответа.

Необходимо учитывать, что не каждый LLM API поддерживает одновременно потоковую передачу и строгий структурированный вывод.

# 10. Memory Engine — долговременная память

## 10.1. Основной принцип

Память RAMVI не ограничивается контекстным окном LLM.

История хранится отдельно и передаётся модели выборочно.

## 10.2. Виды памяти

**Working Memory**

Текущий диалог, последние сообщения, активные задачи.

**Profile Memory**

Явные предпочтения пользователя, настройки общения, учебные интересы.

**Episodic Memory**

Значимые события прошлых разговоров.

**Semantic Memory**

Устойчивые сведения, факты и связи.

**Behavioral Memory**

Результаты взаимодействий, предпочтительные реакции, обратная связь.

**Character State**

Текущее состояние персонажа, не тождественное долговременным воспоминаниям.

## 10.3. Хранение

Для первой версии рекомендуется SQLite с возможностью расширения поискового индекса.

При развитии допускается использование PostgreSQL/pgvector или другого совместимого решения.

Записи памяти должны содержать:

```json
{
  "id": "memory_001",
  "type": "learning_difficulty",
  "subject": "english_pronouns",
  "value": "Часто путает he и she",
  "confidence": 0.94,
  "occurrences": 14,
  "first_seen": "2026-10-20",
  "last_seen": "2026-11-13",
  "status": "active",
  "source_ids": ["event_14", "event_39"]
}
```

## 10.4. Извлечение памяти

Использовать комбинированный поиск:

- Семантическая близость.
- Совпадение тем.
- Сущности и участники.
- Актуальная задача.
- Частота повторений.
- Значимость.
- Давность.
- Незавершённые события.

Нельзя полагаться исключительно на поиск по текстовым embeddings.

## 10.5. Консолидация

Повторяющиеся воспоминания объединяются.

Противоречивые записи не должны автоматически превращаться в подтверждённые факты.

Система обязана различать:

- Сказанное пользователем.
- Подтверждённые наблюдения.
- Интерпретации модели.
- Неподтверждённые предположения.

## 10.6. Ограничение контекста

Context Builder формирует запрос к LLM из:

```text
System instructions
+ Character definition
+ Current emotional state
+ User preferences
+ Current task
+ Recent messages
+ Relevant memories
+ User input
```

Для каждого блока устанавливается отдельный бюджет токенов.

При нехватке места в контексте должны удаляться менее значимые воспоминания, а не базовые инструкции и текущая задача.

# 11. Behavioral Adaptation Engine

## 11.1. Назначение

Изменять манеру поведения персонажа на основании накопленного опыта, не меняя веса LLM.

## 11.2. Источники обратной связи

- Явная положительная или отрицательная оценка.
- Прямые пожелания пользователя.
- Повторяющиеся предпочтения.
- Результаты выполнения задачи.
- Реакции на шутки и эмоциональные ответы.

Неоднозначные сигналы нельзя считать достоверной оценкой.

## 11.3. Правила адаптации

Адаптация должна происходить постепенно.

Единичное взаимодействие не должно автоматически менять устойчивый характер.

Необходимо предусмотреть:

- Ограничения диапазона изменений.
- Скорость адаптации.
- Уровень уверенности.
- Историю изменений.
- Возможность сброса.
- Отдельные настройки для разных пользователей.
- Приоритет прямых пользовательских границ.

## 11.4. Сохранение характера

Персонаж не должен превращаться в полностью другого персонажа после нескольких разговоров.

Например, саркастичный профиль может научиться выбирать более удачные моменты для шуток, не теряя общей склонности к иронии.

При этом допустимость шутки определяется не только характером, но и текущей ситуацией, согласием пользователя и назначением взаимодействия.

# 12. Context Orchestrator

Центральный компонент, отвечающий за подготовку запросов к LLM.

Обязан:

1. Получить пользовательское сообщение.
2. Определить активную задачу.
3. Запросить релевантную память.
4. Получить параметры персонажа.
5. Получить эмоциональное состояние.
6. Сформировать контекст в пределах бюджета.
7. Отправить запрос в выбранную LLM.
8. Валидировать ответ.
9. Передать речевые сегменты и анимационные команды.
10. Обновить состояние и кандидаты на запись памяти.

Обработка памяти должна быть отделена от непосредственного воспроизведения ответа, чтобы не создавать лишних задержек.

Система должна поддерживать отмену, повторы запросов и переключение LLM.

# 13. Provider Abstraction

RAMVI должен поддерживать заменяемые адаптеры:

```typescript
interface LLMProvider {
  generate(request: LLMRequest): AsyncIterable<LLMEvent>;
}

interface SpeechProvider {
  synthesize(request: SpeechRequest): AsyncIterable<AudioEvent>;
}

interface RecognitionProvider {
  recognize(stream: AudioStream): AsyncIterable<RecognitionEvent>;
}

interface AnimationProvider {
  apply(event: CharacterEvent): void;
}
```

Каждый адаптер обязан сообщать свои возможности:

- Поддержка потоковой работы.
- Доступные языки.
- Доступные голоса.
- Поддержка эмоциональных инструкций.
- Наличие таймкодов.
- Поддержка отмены.
- Приблизительная стоимость использования.

При переключении поставщика должны сохраняться профиль, память и состояние персонажа.

# 14. Событийная модель

Внутренние события:

```text
user.speech_started
user.speech_partial
user.speech_completed

llm.response_started
llm.segment_ready
llm.response_completed

character.emotion_changed
character.animation_requested

voice.audio_started
voice.audio_completed

conversation.interrupted

memory.candidate_created
memory.updated

behavior.feedback_received
behavior.parameters_updated
```

Каждое событие должно иметь идентификатор сессии, временную метку и идентификатор текущего ответа.

При перебивании старые события не должны применяться к новому ответу.

# 19. Тестирование и критерии приёмки

## 19.1. Характер

Проверить, что выбранный профиль сохраняет узнаваемые особенности после серии из 100 реплик.

Персонаж не должен использовать одну и ту же шутку или шаблон при каждом похожем событии.

## 19.2. Память

Проверить:

- Сохранение фактов между перезапусками.
- Извлечение информации после сотен сообщений.
- Учет повторяющихся событий.
- Обновление устаревших фактов.
- Отсутствие придуманных воспоминаний.
- Удаление воспоминания по запросу пользователя.

## 19.3. Эмоции

Проверить сценарии:

- Неожиданная информация.
- Уместная шутка.
- Провокация.
- Серьёзная задача.
- Продолжительный спокойный разговор.
- Резкая смена темы.
- Изменение поведения после обратной связи.

Оценивать уместность реакции, а не просто наличие эмоциональной метки.

## 19.4. Голос

Провести сравнительное тестирование русской речи на нескольких TTS-провайдерах.

Особенно проверять:

- Сарказм.
- Удивление.
- Возмущение.
- Иронию.
- Паузы.
- Смешение русского и английского.
- Смену эмоций между сегментами.

## 19.5. Анимация

Проверить:

- Совпадение эмоций голоса и изображения.
- Корректность переходов.
- Отсутствие зависших анимаций.
- Перебивание ответа.
- Переключение голоса.
- Продолжительную работу без утечек памяти.

## 19.6. Адаптация

Сравнить персонажа до и после серии контролируемых взаимодействий.

Проверить, что:

- Явная обратная связь учитывается.
- Неоднозначная реакция не интерпретируется как достоверное одобрение.
- Положительные изменения сохраняются между сессиями.
- Исходный характер остаётся узнаваемым.
- Настройки пользователя имеют приоритет над адаптацией.

## 19.7. Сравнение с human_brain

Использовать идентичные сценарии для:

1. Обычного LLM-контроллера.
2. LLM + память + параметрический Personality Engine.
3. LLM + память + human_brain.

Сравнивать:

- Уместность реакции.
- Последовательность характера.
- Способность учитывать прошлый опыт.
- Скорость адаптации.
- Потребление ресурсов.
- Стабильность поведения.
- Количество ошибочных реакций.

Утверждение о преимуществе human_brain допускается только по результатам повторяемых тестов.

Реализация считается готовой к первой полноценной демонстрации, если пользователь может:
