# Чат (UI-02, пункт 3.4)

Оболочка Avalonia (`desktop/`) запускает процесс сервиса и говорит с ним по локальному HTTP.
Модель, история и лимиты живут в сервисе; оболочка только показывает и отправляет.

## Процессы

```
RAMVI (C#) ──запуск──▶ python -m ramvi_service.app --data-dir …   (ключ в RAMVI_UI_TOKEN)
    │                     │  печатает {"event":"ready","port":N}
    └─HTTP 127.0.0.1:N────┘──▶ EngineManager ──▶ EngineProcess (ramvi-engine serve)
```

- `desktop/src/Ramvi.Desktop/Services/ServiceHost.cs` — запуск сервиса, ожидание `ready`, остановка.
  Сервис получает `RAMVI_EXIT_WITH_PARENT=1` и выходит сам, если оболочка умерла.
- Для разработки: `RAMVI_ROOT`, `RAMVI_PYTHON`, `RAMVI_DATA_DIR`, `RAMVI_SERVICE_ARGS_JSON`
  (например `["--engine-command-json", "[…fake_engine.py]"]`), `RAMVI_LANGUAGE`.

## API `/ui/v1` (`service/ramvi_service/ui_api.py`)

Только 127.0.0.1, заголовок `Authorization: Bearer <ключ>`, проверка `Host`.

| Запрос | Что делает |
|---|---|
| `GET /status` | состояние движка и лимиты вложений |
| `GET /models` | установленные модели |
| `GET /chats`, `POST /chats` | список (новые сверху, флаг `generating`), новый диалог |
| `GET /chats/{id}/messages`, `DELETE /chats/{id}` | история, удаление |
| `POST /chats/{id}/send` | поток SSE: `user`, `status`, `reasoning`, `text`, `done` |
| `POST /chats/{id}/regenerate` | поток SSE: `regenerate` (какие ответы убраны), затем как send |
| `POST /chats/{id}/stop`, `/clear`, `/model`, `/title` | остановка, очистка, смена модели, заголовок |

Ошибки — `{"error":{"code","params"}}`; код — ключ перевода из `i18n/<язык>.json`.
Обрыв соединения клиента отменяет генерацию; ответ сохраняется с `finish = cancelled`.

## Хранилище

Миграция ядра v2 (`storage/ramvi_storage/schema.py`): у сообщений есть `reasoning`, `finish`
(`stop` / `length` / `cancelled` / `error`) и вложения. Thinking хранится отдельно от ответа.

## Вложения

Лимиты по умолчанию (`ramvi_service.chat.Limits`): 5 файлов, 128 КБ на файл, 256 КБ всего,
32 000 символов текста. Оболочка проверяет те же лимиты до отправки (`AttachmentReader`):
размер — до чтения файла, только UTF-8 без нулевых байтов, BOM убирается. Сервис проверяет снова.

## Проверки

- `tests/test_chat.py` — сервис, HTTP и поддельный движок `tests/fixtures/fake_engine.py`
  в настоящих процессах.
- `desktop/tests` (`dotnet test desktop/tests/Ramvi.Desktop.Tests`): модель представления,

Состояния интерфейса с действиями восстановления — ниже (3.5).

## Состояния интерфейса (UI-03, пункт 3.5)

Состояние считает `MainViewModel.State`; при проблеме над диалогом появляется плашка
(`Banner`): заголовок, текст причины и кнопки восстановления.

| Состояние | Откуда | Действия |
|---|---|---|
| Подключение | сервис ещё запускается | — (строка состояния) |
| Нет модели | список моделей пуст; `chat.no_model`, `*.model_not_found` | «Обновить список»; «Выбрать другую модель», если модели есть |
| Загрузка весов | событие потока `status: loading` | «Стоп» |
| Готова | связь есть, модели есть, ответа нет | ввод и «Отправить» |
| Генерирует | идёт ответ | «Стоп» (кнопка у поля ввода) |
| Ошибка | `engine.start_failed`, обрыв связи, сбой запуска сервиса и прочее | «Повторить», «Скрыть» |
| Недостаточно памяти | `engine.no_memory` | «Выбрать другую модель», «Повторить» + совет закрыть программы |
| Модель несовместима | `engine.incompatible` | «Выбрать другую модель» |
| API занят | `api.busy` (очередь модели полна), `chat.busy`, `chat.busy_timeout` | «Повторить» |
| Нет доступа к каталогу | `engine.no_access`, `engine.model_missing`, `storage.no_access` | «Открыть папку» (если папка есть), «Выбрать другую модель», «Повторить» |

«Повторить»: при обрыве связи или сбое запуска сервиса — заново запустить сервис;
иначе — ответить заново на последнее сообщение (regenerate).

Причину сбоя движка сервис берёт из последней трассировки Python в его выводе
(`engines.classify_failure`): `NoMemoryPlan`/`OutOfMemoryError`/`MemoryError`/«out of memory» →
нехватка памяти, `NotImplementedError` → несовместима, `PermissionError` → нет доступа,
`FileNotFoundError` → нет файла. Такие сбои перезапуск не исправит, поэтому ошибка приходит
сразу (замер с поддельным движком: 0,5 с вместо примерно 31 с пяти перезапусков). Неизвестная
причина перезапускается по политике 3.3 и затем даёт `engine.start_failed`. `GET /status` отдаёт
последнюю причину в `engine.problem`.

Папка данных проверяется на запись до открытия базы; при ошибке сервис печатает
`{"event": "error", "code": "storage.no_access", ...}` и выходит с кодом 3.

Тесты: `tests/test_ui_states.py`, `desktop/tests/.../UiStateTests.cs`, `ServiceHostTests.cs`.
Не проверено: настоящий движок при нехватке памяти и с несовместимой моделью (сбой
имитирует поддельный движок), Windows. Уменьшить контекст или сменить режим из интерфейса
пока нельзя — только совет в тексте. Импорт модели для состояния «Нет модели» — пункт 3.8.

## Первый запуск (UI-01, пункт 3.6) и импорт GGUF (3.8)

Пока в `settings.json` папки данных нет `onboarding_done: true`, после подключения к
сервису поверх окна открывается мастер (`OnboardingViewModel`):

1. **Проверка компьютера** — `GET /ui/v1/system`: профиль железа (4.1) и проверки
   ОС, процессор, память, видеокарта, диск, бэкенд со статусом ok / warn / fail / unknown.
   Бэкенд (torch + CUDA) проверяется в отдельном процессе тем же интерпретатором,
   что запускает движок; сервис сам torch не загружает. Результат кешируется до перезапуска.
2. **Модель** — выбор установленной или «Подключить файл модели…» → `POST /ui/v1/models/import`
   `{"path": "<полный путь>"}`. Файл **не копируется**: в базе хранится путь, выбор файла —
   согласие на это (текст под кнопкой). Перед регистрацией читается заголовок GGUF
   (стандартная библиотека): сигнатура, версия 2–3, `general.architecture` из поддерживаемых
   движком (`qwen3`), тип квантования. Повтор того же файла — та же запись;
   одинаковое имя из другой папки получает суффикс `-2`.
3. «Начать» или «Пропустить» → `POST /ui/v1/onboarding {"model_id": ... | null}`.

Модель новых чатов после перезапуска — `settings.default_model`: выбор в мастере, затем
последний явный выбор модели в чате. История чатов хранится в базе (3.2/3.4).

Проверки: `tests/test_onboarding.py` (проверки железа, заголовок GGUF, ошибки импорта,
выбор и история после перезапуска сервиса), `desktop/tests/.../OnboardingTests.cs` и окно
без экрана. Синтетический GGUF из тестов читается так же читалкой движка
(`ramvi_engine.formats.gguf`). Не проверено: импорт настоящего файла модели (на Mac их нет,
есть на ASUS), Windows. Рекомендации и каталог с загрузкой — раздел 4 (4.2–4.6).
GGUF-движку дополнительно нужен токенизатор (`--tokenizer`, по умолчанию Qwen3-8B из кеша HF) —
импорт его не проверяет.
