# Контракт API и событий — 2.5

`ramvi_engine.protocol` — лёгкий общий контракт: API `1.0`, event envelope `1`, независимые версии capabilities/resources/metrics. JSON schema версий доступна через авторизованный `GET /engine/versions`; `/health` также сообщает версии и идентификатор запущенного экземпляра.

Каждый JSON/SSE/NDJSON ответ содержит `X-RAMVI-API-Version` и `X-RAMVI-Event-Version`. Отсутствие заголовка версии запроса сохраняет работу прежних клиентов. Клиент может передать `X-RAMVI-API-Version: 1.x`: совместимая major-версия принимается, несовместимая отклоняется с 426. Неверный `X-Request-ID` отклоняется с 400. Сервер возвращает проверенный/сгенерированный request ID в заголовке; API-ключ не превращается в поле события.

## Envelope

Каждое событие имеет ровно поля:

- `version`, `type`, `payload`;
- `request_id`, `run_id`, `module_id`, `session_id`, `response_id`;
- `event_id`, `sequence`, `monotonic_ns`.

Обязательные request/module/event ID проверяются, остальные ID могут быть null. `version` — целое без bool/float; монотонное время и последовательность — неотрицательные целые. Sequence растёт внутри EventFactory ответа, общий cursor журнала — отдельный счётчик. Интервалы не вычисляются вычитанием Unix-времени. JSON ограничен глубиной и размером; NaN, бесконечности и лишние поля envelope запрещены. Возвращается независимый проверенный снимок.

Core payload имеют строгие наборы полей/типов: `generation.started/delta/completed/failed`, `engine.loading/ready/unloaded/failed/oom`. Будущие события каталога, загрузок, Agent и Voice из раздела 10 ТЗ добавляются со своими схемами при реализации соответствующих подсистем; сейчас они не объявлены работающими событиями. Модульные типы используют `module.<module_id>.<name>` и регистрируются Host со строгой EventSpec.

HTTP-обработчик задаёт контекст запроса; payload модели не может подменить module/session/owner. В публичном Engine API module_id остаётся `engine`. Внутренний Host создаёт контекст по выданной им Authority и отбрасывает чужие/поздние ответы; [модульный контракт](MODULE_CORE.md). `request_id` служит корреляцией, сам по себе не выдаёт разрешений.

## Выдача и совместимость

Стандартные OpenAI/Anthropic/Ollama потоки сохранены. Их payload и usage не заменяются внутренним envelope. Новые события Engine читаются через авторизованный `GET /engine/events?after=<cursor>&request_id=<id>`; request_id необязателен. Журнал ограничен; `gap` сообщает потерю части инкрементальной истории, поле cursor нужно сохранять. Первый запрос без cursor возвращает только сохранённый хвост, не обещает полную историю. Это диагностика, а не постоянное хранилище диалогов.

Generation events содержат дельты ответа и поэтому требуют того же доступа, что и генерация. В отличие от числового MetricsStore журнал событий может содержать текст ответа. Очереди модулей отдельные и ограниченные, отписка/отмена response удаляют устаревшую выдачу. Планировщик не получает полномочий из событий.

`POST /engine/cancel {"request_id": "..."}` отменяет только указанный запрос, включая ожидающий и поздно поступивший. Ограниченные tombstones действуют 60 секунд; Host использует уникальные ID. Ожидающий отменённый запрос снимается без ожидания завершения чужого активного запроса. Пустое тело `{}` сохраняет прежнюю глобальную отмену активной генерации для доверенного администратора Engine; module Provider использует только адресную отмену.

## Проверка

Проверяются несовместимые версии, обязательные ID/строгие типы, неизвестные payload-поля, конечный JSON/лимит, снимки и bounded replay, настоящая HTTP-корреляция, а также неизменность прежних обработчиков после удаления только новых расширений из AST. Это не общее версионирование будущей БД: её миграции относятся к этапу 3.
