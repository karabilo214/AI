# Автоматический план памяти и журнал — пункт 2.6

Контракт реализован в `planning/automatic.py` и подключён в `model_loader.py`. Метаданные и общий `ResourceEstimate` используются до загрузки GPU-весов; после загрузки фактическое размещение публикуется через `engine.placement_decision`. Это ограниченный выбор допустимого бюджета, а не доказанный оптимум скорости.

## Режимы и настройки

`ModelConfig.planning` принимает `PlanningOptions`; `None` сохраняет прежнюю загрузку и native autofit. Конфигурация сериализуется через JSON: вложенный словарь `planning` восстанавливается в тот же класс.

- `mode="auto"`: выбирается наибольшее число resident-слоёв, проходящее оценку VRAM и собственной RAM. Перебирается не более двух наборов по `layers + 1` кандидатов — сначала с явно указанным draft, затем без него, если `draft="auto"`.
- `mode="manual"`: требуется resident. Любой явно заданный resident также означает ручное размещение. План не меняется при startup OOM; для managed dense GGUF отключается автоматическое runtime-вытеснение слоёв. Legacy native-путь сохраняет прежнее поведение.
- `reserve_bytes`: явный запас; если не указан, политика выбирает 1/8 доступной VRAM, в пределах 64 MiB–1 GiB. Это настройка, не измерение аппаратных накладных расходов.
- `max_batch`: верхняя граница из `1,2,4,8,16` для speculative verification и legacy-prefill chunks. Автоматически выбирается наибольшая допустимая граница для контекста, по умолчанию 16; при наблюдаемом startup OOM она уменьшается. Неизмеренный остаточный запас поверх уже учтённого резерва не используется как основание для уменьшения пачки и предполагаемого ускорения. Постоянные native decode-массивы остаются размером 16 и **всегда оцениваются как batch=16**. Низкоуровневый прямой process до 16 токенов сохраняет свой контракт.
- `draft="auto"|"on"|"off"`: никакая новая draft-модель автоматически не ищется/не скачивается. Учитывается только явно заданная модель, с её весами/KV/буферами. `on` требует имя и batch не меньше 2. `auto` может отключить её, если совместный бюджет не проходит.
- `prefill="auto"|"legacy"|"blocked"`: auto сохраняет legacy. Blocked-prefill остаётся явной необязательной настройкой для плотных моделей и применяется начиная с 256 токенов; MoE её отклоняет. Измеренное распределение слоёв также остаётся отдельной opt-in возможностью. Не подтверждённые экспериментальные пути не включаются по умолчанию.
- `allow_paging=True`: нехватка RAM под файловый working set допускается с явным отрицательным `assessment.estimated_fit` и предупреждением в reasons. Собственные RAM-массивы должны помещаться. При `False` учитывается полный `ram + mapped`, как в ResourceEstimate.

Режимы размещения соответствуют существующим исполнителям: HF — GPU/stream/CPU; GGUF dense — GPU/stream/CPU или hybrid (с draft; без draft — B.6, см. ниже); GGUF MoE — CPU-префикс и GPU-суффикс. CPU-only backend из этого не появляется.

`preview_plan(config)` возвращает тот же JSON-совместимый план для CLI и подбора моделей без загрузки весов на GPU. Ошибки архитектуры, отсутствующей CUDA и невозможного бюджета не объявляются успешной загрузкой.

## Прогрев и OOM

Auto после загрузки делает ограниченный прогрев: не более 32 токенов prefill и одного прохода до выбранной границы batch. KV-префикс после прогрева инвалидируется. Не выполняется бесконтрольное повышение resident по предварительно свободной памяти; остаётся выбранный бюджет либо безопасное native-вытеснение при прогреве.

До выдачи первого пользовательского токена startup OOM допускает ограниченные повторные загрузки: по умолчанию 4 попытки (настройка 1–16). Resident уменьшается, batch делится пополам, prefill возвращается в legacy, а необязательный auto-draft отключается. Main/draft закрываются и синхронизируются перед повтором. `LoadFailure` с незавершённым DMA/закрытием не перехватывается как безопасный OOM для повтора: владельцы сохраняются lifecycle для исправного unload.

Во время генерации используется существующий механизм dense GGUF: откат согласованного KV, восстановление RNG и вытеснение слоёв с ограниченным числом повторов. Фактические изменения обнаруживает lifecycle observer и записывает в журнал. В manual этот механизм отключён; OOM возвращается вызывающему коду. HF и MoE не получают выдуманного безопасного воспроизведения частично выданного sampling-ответа: их runtime OOM инвалидирует контекст и возвращает ошибку, после которой нужен unload/restart. Startup fallback для этих архитектур работает до публикации результата.

Ни резерв, ни ResourceEstimate не гарантируют отсутствие OOM: исключения compression, CUDA context, JIT, allocator, загрузочные пики и дисковый paging зависят от оборудования и весов. Нельзя делать вывод об ускорении по числу resident-слоёв.

## Фактический план и журнал

`placement_decision` содержит первоначальные ресурсы/assessment, выбранные параметры, причины, `actual_placement`, `actual_resident`, область действия batch и `estimate_status`. Если native-восстановление изменило слои, старый ResourceEstimate помечается `stale_after_runtime_change`, не выдаётся за точный новый расход памяти.

Пишется ограниченный JSONL в каталоге данных `planning/session-<id>.jsonl`, один журнал на управляемую сессию с повторным использованием при restart. Максимум 256 последних записей, обновление через временный файл и atomic replace. События: decision, load_oom, loaded, actual, error; время монотонное. В журнал не передаются prompts, ответы, token IDs или ключи; только параметры и размещение. Ошибка файловой записи отражается как `journal_error`, не подменяет ошибку модели и не оставляет lifecycle lock захваченным.

## Проверка

Локальные тесты проверяют ручной бюджет, границы resident/batch, ограниченный поиск, мягкий файловый working set и жёсткую собственную RAM, ручной OOM без изменения плана, startup retry и отключение необязательного draft, сохранение владельца при неудачном закрытии, запись/ограничение/конкурентное обновление журнала и наблюдение фактического размещения. Реальная Python-логика native generate проверяется на решаемой контрольной последовательности при cap 1/2/4/8/16; числовые CUDA-ядра этим не проверяются. Аппаратную проверку и сравнение токенов проводит итоговый экзамен раздела 2.

## Гибрид без угадывателя (B.6)

Замер 2026-11-17 (ноутбук RTX 5060 8 ГБ, qwen3 14B Q4_K_M, без угадывателя, запрос 1536 токенов):
чтение запроса 53–55 с, из них 9 слоёв на процессоре — 37,9 с, перекачка 8 слоёв по шине — 0,1 с.
Поэтому для сжатых GGUF Qwen3 план без угадывателя сначала пробует слои процессора как «hyb»:
одиночный шаг по-прежнему считает процессор, а длинный запрос (и пачка до 16 слов) перекачивает
такой слой по шине и считает его в видеокарте; новые строки кэша копируются в RAM. Цена —
закреплённая копия весов этих слоёв в RAM и их кэш k, v в видеокарте (fp16); не помещается — тот же
план с обычными «cpu». Несжатые F16/F32 (3.18) остаются на процессоре. Кэш k, v гибридного слоя
хранится в fp16 и на процессоре — как с угадывателем, поэтому текст совпадает с режимом «с
угадывателем», а не с прежним «cpu» побитно.

Гибриду нужен кэш k, v этих слоёв в видеокарте (14B, контекст 4096, 9–10 слоёв ≈ 144 МБ), поэтому
план, если гибрид не помещается при том же числе слоёв видеокарты, пробует его на 1–2 слоя меньше и
только потом — обычные «cpu». Замер (ноутбук RTX 5060 8 ГБ, 14B, 1536 слов, вместе с подобранным
блоком ядра): чтение запроса 53,2 → 14,8 с; генерация 64 слов при том же числе слоёв видеокарты
6,4–6,5 → 6,1–6,3 ток/с.
