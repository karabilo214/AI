# Контрольный прогон модели (4.7 AUTO-05)

Код: `service/ramvi_service/control_run.py`; использование — `model_fit.apply_control`,
`recommend.py`, `engines.EngineManager.ensure(resident=…)`. Тесты: `tests/test_control_run.py`.

## Когда

- Сам после скачивания модели из каталога (4.3), если на компьютере есть NVIDIA.
- По запросу: `POST /ui/v1/models/{id}/control`; состояние — `GET /ui/v1/models/{id}/control`
  (`queued` / `running` / `done` + `result` / `failed` + `error`).

Модель общая: прогон занимает её слот (`SharedLLM.exclusive`), поэтому идущий ответ чата не
обрывается. Если до прогона была загружена другая модель, после прогона она загружается обратно.

## Что делает

1. Модель загружается заново так же, как для чата: контекст профиля задачи (4.5) и автоматический
   план движка.
2. Прогрев (8 токенов, не в счёт), затем три запроса по 64 токена: короткий, длинный (синтетический
   текст примерно на половину контекста, не больше ~4096 токенов) и снова короткий.
3. Меряется:
   - время до первого токена и ток/с — на стороне сервиса, от запроса до ответа;
   - пики RAM и VRAM и план слоёв — из `ramvi_metrics` движка (провайдер отдаёт их только по
     `with_metrics=True`, остальные потребители потока ничего нового не видят);
   - page faults процесса движка: на Windows — все (мягкие и жёсткие), на Linux — чтения с диска
     (`majflt`), на macOS — нет.
4. Результат сохраняется в `model_profiles`. Ключ — модель + отпечаток железа + контекст; в
   результате же лежит SHA-256 файла. У импортированной модели хеш считается один раз и
   записывается в модель. Отпечаток (`hardware_key`: процессор, ядра, RAM, NVIDIA, драйвер)
   хранится только локально.

## Как используется

- **Скорость.** У установленной модели при том же железе и контексте вместо оценки
  показывается «замер на этом ПК: X–Y токенов/с» (`compat.speed_here`), а в `compat.control` —
  ток/с, время до первого токена, пики памяти, page faults и план. Если файл заменили (другой
  SHA-256), замер не показывается.
- **Нестабильность.** Если был сбой или скорость коротких запросов разошлась больше чем на 25 %,
  прогон помечается нестабильным: причина `compat.reason.unstable`, и в выборе (4.6) такая
  модель идёт после стабильных.
- **Нехватка памяти при генерации.** План движка берётся из события ошибки. Модель загружается
  заново с 0,75 от прежнего числа слоёв в видеопамяти, и прогон повторяется один раз. Если
  удалось, безопасный план сохраняется, и следующие загрузки этой модели при том же железе и
  контексте сразу берут его (`EngineManager.resident_for`); причина — `compat.reason.rolled_back`.
  Если и повтор не прошёл, ничего не сохраняется. Нехватку памяти **при загрузке** движок и
  раньше обрабатывал сам: повторял попытку с меньшим планом.

## Проверено

На поддельном движке (Mac): замер, ключ и хеш, замер вместо оценки, нестабильность, откат при
нехватке памяти с сохранением и повторным использованием плана, неудачный откат,
возврат прежней модели, автозапуск после скачивания, сброс замера при замене файла. Тестов 10,
мутаций поймано 10 из 10.

**Не проверено на настоящей видеокарте** — нужен прогон на компьютере с NVIDIA.
