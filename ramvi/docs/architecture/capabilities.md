# Карта возможностей RAMVI Engine — ENG-02

Это карта реализованных путей кода, **не результат проверки доступности оборудования или экзамена всех моделей**. Поддержка архитектуры не гарантирует загрузку любого файла с таким именем: конфигурацию, формы/типы тензоров и токенизатор проверяют загрузчики. Неизвестные сочетания считаются неподдерживаемыми.

## Backend × архитектура × формат

| Backend | Формат | Архитектура | Тип | GPU resident | Stream | CPU + GPU | Hybrid | Draft | JSON / Schema | Tools |
|---|---|---|---|---|---|---|---|---|---|---|
| CUDA | HF safetensors | qwen3 | Dense | Да | Да | Да | Нет | Условно | Нет | Условно |
| CUDA | GGUF | qwen3 | Dense | Да | Да | Да | Да | Условно | Условно | Условно |
| CUDA | GGUF | qwen3moe | MoE | Если все слои помещаются | Нет | Да | Нет | Условно | Условно | Условно |
| CPU-only | Любой | Любая | Любой | Нет | Нет | Нет | Нет | Нет | Нет | Нет |
| Metal / ROCm | Любой | Любая | Любой | Нет | Нет | Нет | Нет | Нет | Нет | Нет |

Названия режимов в JSON:

- `gpu`: все слои resident на CUDA.
- `stream`: часть слоёв подкачивается в CUDA, CPU не считает слои.
- `cpu_gpu`: часть слоёв считает CPU, остальное — CUDA; плотный движок может также подкачивать другие слои.
- `hybrid`: плотный движок меняет CPU/подкачку для слоя в зависимости от размера прохода. Это внутренний режим размещения, не отдельный backend.

Даже при `resident=0` выходная голова, нормировки и другие вычисления остаются на CUDA. CPU-only и запуск генерации на Mac через Metal не реализованы. Для CUDA нужны подходящие устройство, PyTorch/CUDA и Triton; CPU-ядра могут использовать native/Numba, а MoE требует native qmm. Матрицы CPU в HF требуют BF16. GGUF `validate_qwen` допускает Q4_K/Q6_K/F16/F32 для плотных матриц, только Q4_K/Q6_K для экспертных; другие тензоры проверяются отдельно. Возможность распаковать тип в `formats/gguf.py` не означает поддержку этого типа всем inference-путём. Масштабирование и частичный RoPE GGUF не поддержаны.

## Возможности ответа

- **Draft:** проверка совместимости словарей/токенизаторов, достаточная память и greedy-декодирование. При sampling используется обычный путь; наличие draft не означает его использование в каждом запросе/шаге. Совместимость не следует выводить только из названия семейства.
- **JSON / JSON Schema:** GGUF dense/MoE имеют маску грамматики. Нужны xgrammar, совместимый токенизатор и поддерживаемая схема. Ограничены сложность/размер схемы, внешние `$ref` запрещены. Лимит вывода, stop, отмена или сбой могут оборвать JSON; потребитель всё равно проверяет завершённость и схему. HF Engine отклоняет грамматическое ограничение.
- **Tools:** передача описаний в chat template и разбор модельных tool calls в совместимых API. Нужны соответствующие шаблон и качество модели; вызов не гарантирован. Движок не исполняет инструменты и не выдаёт разрешения Agent.
- Вход/выход — текст. Vision, аудио, STT, TTS, эмоции и память Character не являются возможностями этого backend.
- Один активный запрос генерации; `n=1`; контекст фиксируется при загрузке. Frequency/presence/repeat penalties, sampling top_k, logprobs, logit_bias, suffix/echo не поддержаны в полном виде; точные допустимые значения проверяет `server/validation.py`.

## Машиночитаемый контракт

Без модели, GPU и импорта вычислительных библиотек:

```sh
python -m ramvi_engine capabilities
```

Python: `ramvi_engine.capabilities.capability_catalog()`. HTTP: `GET /capabilities` на запущенном сервере, с обычной авторизацией сервера (`Authorization: Bearer …` или `x-api-key`). Новый маршрут не открывает доступ в обход API-ключа.

Источник контракта — `ramvi_engine/capabilities.py`. Каждый вызов возвращает независимый JSON-совместимый объект:

- `schema_version: 1` — версия именно карты возможностей, не всего API;
- `scope: implementation_catalog`, `runtime_verified: false` — статическая поддержка, не автодиагностика;
- `backends`, `rows` — backend/format/architecture/model_type, режимы, ограничения весов и условия draft/JSON/tools;
- `unknown_combinations: unsupported` — запрещает оптимистичные предположения для новых архитектур;
- `input_modalities`, `output_modalities`, `limits` — общие ограничения;
- только HTTP дополнительно содержит `loaded_model`: распознанные format/architecture, фактические context/placement, наличие draft, флаг маски грамматики и `readiness: not_probed`.

`loaded_model` не проверяет установку xgrammar, содержимое chat template, совместимость произвольной будущей пары draft или доступный запас памяти. Потребитель сопоставляет строку каталога с загруженной моделью и выполняет требуемые проверки; неизвестная модель не получает разрешения по умолчанию. Размещение — снимок, а не обещание неизменности после OOM. Маршрут не запускает inference и не загружает новые веса.

## Источники и проверка

Реализация сверена с `formats/model.py` (`ARCH`, BF16), `core/gengine.py`, `core/moe.py`, `formats/gguf.py` (`validate_qwen`), `core/engine.py` (generate), `generation/constrain.py`, `server/validation.py` и обработчиками API.

Контрактные тесты проверяют консервативную матрицу, неизвестные модели, независимость снимков, CLI с запрещёнными импортами torch/numpy/triton/transformers и HTTP с авторизацией без генерации. Это не новые аппаратные замеры. Автопроверка железа, ResourceEstimate и полноценный lifecycle остаются следующими пунктами плана.

## Режим Thinking-only

`loaded_model.thinking_required` и `chat_template_source` описывают фактически загруженную модель. Для GGUF с явным `general.finetune=Thinking` используется встроенный chat template, а не общий переключаемый шаблон токенизатора. Такая модель всегда генерирует reasoning; `think=false` не превращает её в Instruct-модель. App выделяет reasoning даже когда открывающий `<think>` уже находится в prompt.

До отдельного reasoning-aware grammar adapter JSON-ограничение для Thinking-only отклоняется с понятной ошибкой; `grammar_mask=false`. Для обычных GGUF и HF прежние шаблоны и переключатель thinking сохраняются. Лимит токенов включает рассуждения: ответ с `finish=length` может не содержать финального текста, это не завершённый арифметический ответ.
