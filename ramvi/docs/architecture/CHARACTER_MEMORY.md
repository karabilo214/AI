# Память и состояние персонажа (CHAR-14, пункт 9.14)

Таблицы памяти объявляет сам Character миграцией
[`modules/character/migrations/0001_memory.sql`](../../modules/character/migrations/0001_memory.sql).
Они лежат в собственной базе модуля `data/modules/character/data.sqlite3` (механизм 3.12,
[MODULE_DATA.md](MODULE_DATA.md)), а не в Core: данные Chat, Agent и других модулей недоступны,
потому что это другой файл. Код доступа: `character/ramvi_character/memory.py` (`MemoryStore`).

## Пространства

`memory_namespace` — пара «пользователь + персонаж», id вида `u:owner/c:default`. Каждый запрос
`MemoryStore` содержит этот id, поэтому записи разных пользователей и разных персонажей одного
пользователя не смешиваются даже при одинаковых id записей. Сейчас пользователь один (`owner`,
либо `user_id` из контекста модуля), персонаж — `default`; смена пака или профиля память не меняет.

## Запись памяти (`memory_record`)

Поля из ТЗ 10.3: `id`, `type`, `subject`, `value`, `confidence`, `occurrences`, `first_seen`,
`last_seen`, `status`, `source_ids`. Дополнительно:

| Поле | Значения |
|---|---|
| `kind` | `working`, `profile`, `episodic`, `semantic`, `behavioral` — виды памяти ТЗ 10.2 |
| `origin` | `user_said`, `observed`, `interpretation`, `assumption` — откуда знание (ТЗ 10.5) |
| `status` | `candidate`, `active`, `disputed`, `superseded` |
| `expires_at` | только у рабочей памяти; истёкшая запись не попадает в выборку |

Активным фактом может стать только сказанное пользователем или подтверждённое наблюдение:
интерпретация модели и предположение остаются кандидатом или спорной записью. Правило проверяет
и код, и `CHECK` в самой схеме. `observe` — та же запись встретилась снова: `occurrences + 1`,
`last_seen` обновляется, источники объединяются (не больше 32). `forget` удаляет запись по просьбе
пользователя.

## Character State (`character_state`)

Текущее состояние персонажа хранится отдельно от воспоминаний: одна строка на пространство,
JSON со схемой `ramvi.character.live_state/1` и счётчиком ревизий. Сейчас там эмоциональное
состояние. Модуль пишет его при checkpoint и читает при запуске; если строка есть, она важнее
прежнего JSON-checkpoint. Установки без базы (до 0.9.0) берут состояние из checkpoint и переносят
его в базу при следующем сохранении.
