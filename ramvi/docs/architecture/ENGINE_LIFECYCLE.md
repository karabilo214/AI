# Жизненный цикл Engine — пункт 2.3

`EngineSession` владеет основной моделью, её токенизатором и draft. `ModelConfig` хранит только настройки; повторная загрузка создаёт новые native-объекты в том же процессе. CLI `serve` и `chat` используют сессию и закрывают её в `finally`. Старое прямое создание native-движков оставлено для низкоуровневых проверок.

## Операции

| Операция | Поведение |
|---|---|
| `load()` | Загрузить фиксированный ModelConfig; повторный вызов для готовой модели ничего не дублирует |
| `warmup(tokens, max_new=2)` | Выполнить короткую настоящую генерацию, включая draft; 1–16 новых токенов, проверка token IDs |
| `generate(...)` | Сериализованная генерация; kwargs совместимы с native Engine, draft handle заменяется реальной моделью внутри владельца |
| `cancel()` | Запросить отмену активной генерации; idle cancel не отменяет следующий запрос |
| `unload()` | Запретить новые запросы, отменить текущую генерацию, дождаться её завершения, закрыть загрузчики, синхронизировать CUDA, удалить владельцев и очистить свободную память |
| `restart()` | Последовательные unload/load под одним блокировщиком; повторно использует конфигурацию, а не старую модель |
| `status()` | Снимок состояния без загрузки/генерации |

Состояния: `unloaded`, `loading`, `ready`, `generating`, `unloading`, `error`. Прогрев проходит через генерацию. Ошибка загрузки не считается готовой моделью. Если частично созданный движок не удалось безопасно закрыть, `LoadFailure` передаёт его владельцу; повторный load запрещён до успешного unload. Ошибка генерации тоже требует unload/restart.

Отмена кооперативная: проверяется между вызовами native-генератора. Уже запущенный prefill, CUDA kernel или CPU-операция не прерываются насильно. После отмены поднимается `GenerationCancelled`, частичный ответ не выдаётся как успешно законченный. Сетевой разрыв дополнительно закрывает генератор существующим механизмом GenerationStream.

## Синхронизация и память

Один запрос удерживает lease до завершения разбора текста и итогового события App. Это предотвращает выгрузку токенизатора/модели между последним токеном и формированием ответа. Переход unload/restart блокирует новые генерации. Истечение ожидания блокировки не освобождает память работающего движка. Вызов unload из того же потока, где приостановлен генератор/запрос, требует сначала закрыть этот генератор и возвращает TimeoutError.

При успешном unload:

1. Main и draft закрываются по одному разу на уникальный объект; Loader завершает поток и DMA.
2. Выполняется синхронизация CUDA перед удалением ресурсов. При сбое этого шага владелец сохраняется для повторной попытки.
3. Удаляется ModelBundle; сборщик мусора удаляет циклы, например MoE layer → engine.
4. Для последней управляемой сессии процесса очищаются GPU scratch-кэши `wcomp._SK` и `gkernels._XP`, а также кэши грамматик/компиляторов с их ссылками на токенизатор. Числовые таблицы настроек ядер сохраняются.
5. Вызывается CUDA `empty_cache()`.

Общие кэши не очищаются, пока другая управляемая сессия владеет моделью или загружает её. Одновременный inference нескольких native-моделей в одном процессе через общие scratch-буферы не является новым поддержанным режимом; main/draft работают последовательно в одной сессии. Не смешивать внешние неуправляемые владельцы с управляемой очисткой в одном процессе. Не сохранять native-модели, тензоры, bound methods и внутренний ModelBundle снаружи сессии: внешние ссылки мешают освобождению памяти.

Значение timeout ограничивает ожидание операций, но не гарантирует прерывание зависшего CUDA-драйвера. Принудительное завершение процесса относится к supervisor пункта 2.8. CUDA context остаётся до конца процесса: нулевой `memory_allocated()` не означает отсутствия служебной памяти драйвера. Измерять allocator и driver memory отдельно.

## Python API

```python
from ramvi_engine.model_loader import ModelConfig, create_session

session = create_session(ModelConfig("qwen3:14b", resident=21))
try:
    session.load()
    tokenizer = session.tokenizer  # handle, не удерживает native-модель
    ids = tokenizer.encode("Hello", add_special_tokens=False)
    session.warmup(ids)
    tokens = list(session.generate(ids, 32))
    session.restart()
finally:
    session.close()
```

Для HF использовать имя/папку safetensors, для GGUF — путь или имя существующей модели Ollama. Сам сервис Ollama для чтения локальных файлов не запускается. После load проверяются токенизатор и совместимость draft, сохраняются прежние правила CPU/resident/autofit.

## HTTP API

Управляемый `serve` добавляет маршруты с обычной авторизацией сервера. Конфигурация фиксируется при старте CLI; произвольные пути моделей и настройки из HTTP не принимаются.

| Метод / путь | Тело |
|---|---|
| `GET /engine/status` | Нет |
| `POST /engine/load` | `{}` |
| `POST /engine/warmup` | `{"tokens": [1, 2], "max_new": 2}` |
| `POST /engine/unload` | `{}` |
| `POST /engine/restart` | `{}` |
| `POST /engine/cancel` | `{}` |

Неизвестные поля отклоняются. Недоступная модель даёт 503, отменённая генерация — ошибку отмены (409 до начала потока, существующий stream error после начала), ожидание операции — 504. Legacy App без EngineSession не предоставляет управление native-моделью. `/health` сохраняет прежний смысл доступности процесса; готовность модели проверять через `/engine/status`, не по `/health`.

Это контракт текущего процесса. Версионирование всех событий/API и общий процессный supervisor остаются пунктами 2.5/2.8. Смена модели по HTTP и выгрузка по политике ресурсов здесь не реализованы.

## Проверка

Локальные тесты: повторная загрузка, weakref владельцев, отмена/возобновление, generator.close, ошибки и частичная загрузка, timeout без освобождения активных ресурсов, lease итогового события, счётчик владельцев общих кэшей, авторизация HTTP и сохранение параметров загрузки. Аппаратная приёмка и её ограничения фиксируются отдельным отчётом после завершения проверки.

## Замечание о проверке качества модели

Тест жизненного цикла проверяет сохранение последовательности токенов и освобождение ресурсов, а не улучшение ответов LLM. При диагностике HF Qwen3-0.6B на запрос `Reply with just the number: 2 + 2 =` получен ответ `2` и через native Engine, и через EngineSession, в том числе после warmup. На запрос повторить цифру `4` оба пути дали `4`. Ошибка арифметического ответа не исправлена этим пунктом и не считается его достижением.

В GGUF Qwen3-30B MoE с resident=0 этот арифметический запрос дал `2` со служебной меткой `</think>`; native, managed и managed после warmup выдали одинаковые токены. Контроль повторения `4` прошёл. Причина неверного арифметического ответа не установлена; требуется отдельная сверка с эталоном в 2.7. Это не доказательство корректности математических ядер или качества модели.
