# Обновления (8.3, PORT-04)

Код — `service/ramvi_service/updates.py` (подготовка, применение, откат, проверка по сети), `service/ramvi_service/ed25519.py` (подпись), `packaging/make_update.py` (ключ выпуска и пакет). Требования — раздел 9 ТЗ: подписанный манифест по согласию, staging в отдельной папке, откат, миграция базы с резервной копией, офлайн-архив. Приёмка: неудачное обновление не удаляет историю чатов и модели.

## Пакет

Один zip — и офлайн-архив, и то, что скачивается по сети:

| Файл | Что это |
|---|---|
| `manifest.json` | схема `ramvi.update/1`: продукт, версия, файлы (путь, SHA-256, размер), что удалить, заметки |
| `manifest.sig` | подпись Ed25519 точных байтов `manifest.json` (base64) |
| `payload/<путь>` | новые и изменённые файлы |

Пакет может менять только части комплекта: `ramvi/`, `runtime/`, `modules/`, `RAMVI.exe`, `BUILD.json`, `LICENSE`. Пути — относительные, без `..`, дисков и `\`. **Данные, модели, `settings.json` и сама папка `updates` пакету недоступны** — даже подписанный пакет не может их тронуть (`update.forbidden_path`).

Подпись — Ed25519 по RFC 8032, без внешних библиотек (эталонный код RFC, сверен с тестовыми векторами RFC). Открытые ключи выпусков — `updates.TRUSTED_KEYS`; закрытый ключ хранится только у того, кто выпускает обновления, в репозиторий не попадает. Ключ выпуска создан 2026-11-19 (открытая часть — в `TRUSTED_KEYS`, закрытая — у владельца вне репозитория); без ключей обновления не устанавливались бы (`update.no_trusted_key`).

Выпуск:

```
python packaging/make_update.py keygen --out release-key.hex        # один раз; печатает открытый ключ
python packaging/make_update.py build --bundle <новый комплект> --version 0.8.1 \
    --key release-key.hex --out RAMVI-update-0.8.1.zip --previous <прежний комплект>
```

С `--previous` в пакет попадают только изменившиеся файлы и список удалённых. Версия продукта — `ramvi_service.__version__`, сборка пишет её в `BUILD.json` комплекта.

## Жизненный цикл

1. **Проверка по сети — только по согласию** (`check_online(consent, url)`; без согласия — `update.no_consent`, только HTTPS): `<url>/latest.json` и `latest.json.sig`, подписанные тем же ключом, — версия и адрес пакета.
2. **Подготовка** (`stage`): подпись, версия новее установленной, распаковка в `updates/staging/<версия>` со сверкой SHA-256 и размера каждого файла. Рабочие файлы не меняются. Любая ошибка — ничего не изменено.
3. **Применение** (`apply`, сервис остановлен — его выполняет оболочка перед запуском или CLI): резервная копия базы (SQLite backup API) в `updates/backup/<версия>`; каждый заменяемый или удаляемый файл **переносится** в резервную папку (переименование работает и для занятых файлов Windows), затем на место ставится новый; журнал перемещений пишется в `updates/state.json` до каждого шага. Ошибка посреди применения — сразу откат.
4. **Проверка запуска**: новая версия стартовала — `mark_good`; не стартовала — `rollback`.
5. **Откат** (`rollback`): файлы возвращаются по журналу (добавленные удаляются, удалённые возвращаются). База восстанавливается из копии, только если новая версия успела применить миграции (прежний код такую базу не откроет); изменённая база не удаляется, а сохраняется в `data/backups/ramvi.sqlite3.after-update-<версия>-<время>`. Миграции базы и сами делают резервную копию перед изменением (`storage.migrations`).

**Оболочка** (`ServiceHost.StartWithUpdatesAsync`) перед запуском сервиса спрашивает состояние; есть подготовленное обновление — применяет его; затем запускает сервис: стартовал — `mark-good`, не стартовал — `rollback` и запуск прежней версии. Если прошлый запуск после обновления не дошёл до отметки (`health: pending`), проверка повторяется. Логика отделена от процессов (`WithUpdatesAsync`) и проверена тестами оболочки.

**Интерфейс** — раздел «Обновления» на вкладке «Общие»: установленная версия, «Установить из файла…» (подготовка через `POST /ui/v1/updates/stage`, рабочие файлы не меняются), «Перезапустить и обновить»; после неудачи — «обновление не запустилось, возвращена прежняя версия, чаты и модели не тронуты». Проверка по сети в интерфейс выйдет вместе с сервером обновлений (в сервисе она есть и по умолчанию выключена).

CLI для оболочки: `python -m ramvi_service.updates status|stage --archive <zip>|apply|rollback|mark-good --app-dir … --data-dir …` — ответ одной строкой JSON, ошибка — `{"error": {code, params}}` и код выхода 2.

Тесты: `tests/test_updates.py` (в том числе маршруты интерфейса и CLI в отдельном процессе), `desktop/tests/Ramvi.Desktop.Tests/UpdatesTests.cs` (применение, отметка, откат при неудачном старте, раздел настроек) — векторы RFC 8032, состав пакета, подготовка без изменений рабочих файлов, применение и откат с сохранностью чатов, модели и настроек, сбой посреди применения, восстановление базы после миграции новой версии, отказ при чужой подписи, подмене файла, старой версии, путях в данные/модели/за пределы, проверка по сети без согласия и по HTTP.

## Проверка на Windows (2026-11-19)

Ноутбук с RTX 5060, Windows 11 25H2, копия переносимого комплекта (4,3 ГБ). Пакет 0.8.1 подписан настоящим ключом выпуска и меняет `RAMVI.exe` (105 МБ) и `runtime/python/python312.dll` — оба заняты запущенным приложением (`RAMVI.exe` и четыре процесса Python из копии) — плюс `BUILD.json` и новый файл кода.

| Шаг (приложение запущено) | Итог |
|---|---|
| подготовка | `staged 0.8.1`, 4 файла, рабочие файлы не тронуты |
| применение | все 4 файла заменены (хеши совпали с пакетом), версия 0.8.1; оболочка продолжает работать |
| откат | все файлы вернулись к исходным хешам, новый файл убран, версия 0.8.0 |

Проверка нашла ошибку: откат запускает новый `python.exe`, который уже загрузил **новый** `python312.dll`, а прежний код пытался этот файл удалить — Windows не даёт удалить занятый файл. Теперь откат новые файлы не удаляет, а переносит в `updates/backup/<версия>/rejected` (переименование занятого файла разрешено); если какой-то файл вернуть не удалось, остальные всё равно возвращаются, а интерфейс получает `update.rollback_incomplete` со списком. Исправленный откат прошёл на Windows ровно в этом случае. Найдено и исправлено ещё: в файле состояния сохранялась устаревшая «текущая версия», а отметка прошлого отката оставалась в новом цикле.
