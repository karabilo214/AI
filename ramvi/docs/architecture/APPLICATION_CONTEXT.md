# Контекст приложений и UI-действия (6.11–6.12)

Реализация: `context.py`, `system_context.py`, `native/windows_context.ps1`,
`agent/ui.py`. Использует существующие Authority, GrantStore, Scoped Services,
ToolRunner и ApprovalGate; Character не импортируется.

## Три независимых доступа

| Грант выбранного приложения | Разрешает | Не предоставляет автоматически |
|---|---|---|
| `context.ui` | структура UI, доступное выделение | Screen, действия, внешняя отправка |
| `context.screen` | снимок окна, если провайдер объявил image input | UI-структура, действия, внешняя отправка |
| `agent.control` | предложение UI-действия через Agent | чтение UI/экрана, обход подтверждения |

`egress.text` и `egress.image` — отдельные права внешней отправки конкретного
приложения. Host выдаёт application grants только по явному выбору пользователя
(`approve_application`); wildcard вместо выбранного приложения запрещён. Методов
выдачи этих грантов в RPC модуля нет.

`context.capture` в Scoped Services принимает `kind=ui|screen|auto`. `auto`
использует `capture_best`: сначала достаточная структура/выделение. Если контекста
нет, возвращает понятную недоступность; снимок надо запросить явно с отдельным
Screen-грантом. Нет опроса по таймеру или скрытого облачного анализа.

Ограничения ContextProvider по умолчанию: интервал 0,1 с, ответ до 1 МиБ,
суммарно до 4 МиБ за минуту на владельца; бюджет можно отключить (`None`), интервал
снять (`0`). Хранится только последний snapshot владельца. Снимок привязан к
владельцу, приложению, окну, источнику, времени и версии read-гранта. После отзыва
и повторного разрешения старый снимок не становится действительным.

Сбор/передача получают cancellation token от грантов. Отзыв отменяет незавершённую
операцию, результаты повторно проверяются до выдачи. Уже отправленные внешнему
провайдеру байты вернуть нельзя; sender обязан проверять cancel. Внешние LLM-запросы
через Scoped Services после capture требуют также egress выбранного приложения;
общий `egress.text` не заменяет этот грант. Историю с отозванным контекстом нельзя
повторно передать после reallow: нужна новая сессия модуля.

## Системный адаптер Windows

`SystemContextAdapter.current_target()` предназначен для доверенного выбора цели.
Идентичность приложения — PID и время старта процесса; окно — HWND. Capture
проверяет процесс и foreground до и после сбора. UI Automation отдаёт ограниченное
дерево, ID элементов, доступные паттерны, имена и выделение. Password-элементы
пропускаются. Отпечаток учитывает также значения полей, не сохраняя их отдельно в
журнале. По умолчанию обход ограничен глубиной 5 и 128 элементами.

Screen использует PrintWindow выбранного окна, уменьшает изображение до длинной
стороны 1024; не делает fallback на весь рабочий стол. Неуспех или превышение
бюджета — ошибка. Системный helper имеет ограничение времени и вывода, запускается
без подстановки модельных команд и завершается вместе со своим деревом процессов.
Его JSON-запрос передаётся временным файлом и удаляется после операции.

На Mac системный адаптер пока недоступен (`capabilities`: false). Контракты и
хранилище проверяются на Mac, живой системный адаптер — на Windows. Наличие UIA
не гарантирует пригодность любого приложения: тестовое WinForms-окно под Windows
PowerShell не объявляло паттерны действий; WPF-окно прошло проверку. Для неизвестных
или неподдержанных элементов нет запасных глобальных клавиш и кликов.

## Действия через Agent

Доверенная сборка runtime добавляет `UIControl(context, owner, application,
window_id, adapter, external=provider.capabilities.external).register(tools)`.
Это фиксированная пользователем цель; модель не подставляет другое приложение.

- `ui_context` — свежая структура и выделение, ID снимка и элементов.
- `ui_action` — snapshot ID, element ID, `invoke|set_value`, короткий видимый план,
  новое значение для `set_value`. Возвращает предложение, а не выполняет действие.

ToolRunner отдельно проверяет `context.ui`/`agent.control` (они не зависят от
файловых read/write). Схема, переключатель инструмента и запись в журнал действуют
как для файлов. ApprovalGate показывает цель, план и предлагаемое значение;
`confirm_controls=true` по умолчанию, свой счётчик серии. Выключенная пользователем
проверка файловых записей не выключает подтверждение UI.

После approve повторно проверяются read/control, принадлежность и свежесть
снимка (30 с по умолчанию, `None` снимает возрастной предел). Системный helper заново
проверяет foreground, PID/время старта, отпечаток UI и единственный element ID
перед InvokePattern/ValuePattern. Эти операции адресованы конкретному элементу;
SendKeys, координатных кликов, переключения чужого окна или запуска программ нет.
Снимок расходуется после попытки действия: для следующего требуется новый.
Отказ/неизвестный результат не следует автоматически повторять.

Между проверкой и вызовом UIA нет общей транзакции с чужим приложением. Смена
фокуса/состояния, замеченная при проверке, отклоняет действие; адресный UIA-вызов
не превращается в глобальный ввод в случайно активное окно.

## Приватность и результат

Регистрация UI-инструментов включает приватный журнал runtime: экран/выделение,
вводимое значение, текст плана/итога и diff не дублируются в agent_events/tool_calls.
Сохраняются цель, ID, тип действия, подтверждение и результат/ошибка. В текущий
интерфейс пользователя и модель разрешённый контекст передаётся в памяти.
Перед каждым следующим запросом модели повторно проверяется read-версия; для
внешнего провайдера — app-specific egress, отзыв отменяет идущий запрос.

Обычные файловые запуски сохраняют прежний подробный журнал. Намеренно записанный
пользователем файл и снимок его отката — отдельные данные подтверждённой операции,
а не скрытый журнал экрана. Очистка общая по 6.7.

Проверки: `test_application_context.py`, `test_agent_ui.py`, общие regression-тесты
Agent/Scoped Services и [живой отчёт этапа 6](../reports/EXAM6_AGENT.md).
Выбор приложения, экран агента и настройки доступа в оболочке остаются отдельной
продуктовой работой; данная проверка принимает сервисные контракты и Windows backend.
