# Модули RAMVI и внедрение Character

Статус: основа платформенных контрактов и Module Host реализована; внедрение самого Character остаётся планом этапа 9. Текущие контракты, проверки и ограничения описаны в [основе модулей](MODULE_CORE.md), архитектурное решение — в [ADR-0002](../adr/ADR-0002-module-platform.md). Основание: [Character TZ](../spec/Character-Module/TZ.md) и [архитектурное дополнение](../spec/Character-Module/Add-TZ.md). При расхождении архитектурных формулировок применяется дополнение: RAMVI сохраняет назначение платформы; Character — самостоятельный необязательный модуль. Общий порядок работ и отметки исполнения — в [PLAN.md](../PLAN.md).

## Границы ядра

RAMVI Core здесь означает координацию приложения в `ramvi_service`, а не математический пакет `ramvi_engine.core`. Вычислительный движок сохраняет существующие команды и API. Его запуск не должен требовать Module Host, Character, аудио или UI.

Реализованы движок и лёгкая основа `ramvi_service`: Module Host, авторизация владельцев, Scoped Services, версионированные события, арбитр ресурсов, общий LLM Provider и контроллеры отдельных worker-процессов. Есть scoped JSON-данные с миграциями, подключаемый интерфейс секретов и optional Context Provider с раздельными правами. Это не полный Storage и не готовое десктопное приложение: постоянное хранилище секретов, общая БД/репозитории, UI и продуктовые Chat/Agent/Character ещё предстоят по общему плану. Перечень Shared Services в дополнении включает как готовую основу, так и будущие адаптеры.

| Область | Владелец и границы |
|---|---|
| Модели и генерация | RAMVI Engine; общий LLM Provider в сервисе использует его публичный API и допускает внешние адаптеры |
| Модули | Тонкий Module Host в сервисе: реестр, версии, жизненный цикл, выдача доступных сервисов |
| Конфигурация, события, ресурсы, сохранение | Готовы общие scoped-интерфейсы и общий процессный супервизор; полноценный Storage подключается в этапе 3 без второго параллельного координатора |
| Chat | Обычный чат, его история и интерфейс; без обязательного характера и эмоций |
| Agent | Планирование, инструменты, права, подтверждения и журнал агентных задач |
| Character | Personality, Emotional State, Memory, Adaptation, Context Orchestrator, Response Planner, управление голосом и анимацией |
| STT/TTS/анимация | Адаптеры за интерфейсами; низкоуровневые функции можно повторно использовать, эмоциональная политика принадлежит Character |
| human_brain | Экспериментальный адаптер внутри Character; отключается без влияния на основную работу |

Зависимости: функциональный модуль → публичные контракты сервиса → адаптеры Engine/Storage/ресурсов. Chat и Agent не импортируют Character. В ядре нет ветвлений по конкретным эмоциям, профилям или идентификатору `character`; расширения регистрируются через общий контракт.

## Минимальный контракт расширения

Контракты размещены в `service/ramvi_service/contracts/` без импорта Torch, UI, аудио и запуска сервиса при импорте. Module Host — в `service/ramvi_service/modules/`. Выделять отдельный SDK-пакет следует при необходимости независимого распространения, не создавая второй координатор приложения.

Манифест модуля содержит:

- Уникальный `module_id`, версию пакета и поддерживаемую версию Module API.
- Фабрику/точку входа, обязательные и необязательные зависимости, требуемые возможности сервисов.
- Запрашиваемые разрешения, описание потребностей в ресурсах, версию схемы своих данных.
- Необязательное описание UI-раздела и ресурсов; тяжёлые зависимости загружаются лениво.

Первый реестр рассчитан на встроенные и явно установленные доверенные пакеты. Магазин плагинов и исполнение произвольного стороннего кода не входят в этот этап. Отсутствие пакета, несовместимая версия, цикл зависимостей или ошибка модуля должны давать диагностируемый статус модуля, сохраняя работу остальных разделов.

Для проверки расширяемости реализован небольшой тестовый модуль, запускаемый двумя независимыми worker-процессами: регистрация, активация, собственные настройки, события, остановка и удаление проверяются без изменения кода Host. Fixture находится только в тестах и не входит в обязательные функции продукта.

### Жизненный цикл

Публичные операции: `initialize()`, `activate()`, `deactivate()`, `suspend()`, `resume()`, `dispose()`.

Принятый контракт определяет допустимые переходы, идемпотентные повторные вызовы, таймауты и восстановление после ошибки; реализация и границы описаны в [MODULE_CORE.md](MODULE_CORE.md). `initialize()` проверяет метаданные и готовит лёгкое состояние; захват звука и тяжёлые адаптеры открываются только для явно выбранного режима. При остановке отменяются запросы модуля, закрываются очереди, подписки, таймеры, устройства и его аренды ресурсов; необходимое состояние сохраняется.

Общий module worker уже использует тот же `ProcessSupervisor`, что и отдельный Engine. Его crash/timeout, checkpoint, suspend/resume, обновление и rollback проверяются тестовым модулем. Сам Character worker и его UI/аудио-адаптеры предстоят в этапе 9: наличие общего механизма не означает их реализацию. Интерфейс WorkerController допускает подмену контроллера в контрактных тестах; штатный контроллер использует отдельный процесс.

Обновление модуля реализовано через деактивацию, проверку совместимости, резервную копию и staging-миграцию только его данных, пробную активацию новой версии и откат при неудаче. Chat/Agent и их данные при этом не обновляются. При удалении пакета его данные сохраняются по умолчанию; явное удаление данных ограничено пространством этого модуля.

### Сервисы и изоляция

| Контракт | Реализованная основа и дальнейшее внедрение | Проверка |
|---|---|---|
| LLM Provider | Готовы capabilities, отмена по request ID, общая очередь и локальный Engine adapter; Scoped complete сейчас выдаёт один итоговый ответ. Потоковые/внешние продуктовые адаптеры подключаются отдельно | Контрактные проверки отказа неподдерживаемых JSON/tools/image и отдельной отмены; замена провайдера у реального Character проверяется при его внедрении |
| Module Services | Готовы scoped настройки/JSON-данные, события, ресурсы, SecretBackend и разрешения через аутентифицированный loopback RPC. Полный Storage/OS credential store — этап 3 | Core API не выдаёт чужой namespace или секреты; доверенный Python-код не объявляется OS sandbox |
| Resource Lease | Готовы учёт владельца, FIFO, квоты, отмена active/queued запросов и переиспользование модели поверх ResourceEstimate | Остановка тестового companion не выгружает модель активного Chat; реальные аудиоустройства подключаются своими адаптерами позднее |
| Event Envelope | Используется общий Engine envelope: `module_id`, `session_id`, `response_id`, `event_id`, версия, последовательность и монотонное время; готов bounded EventBus с Host-схемами | События разных владельцев и старого/нового ответа не смешиваются; неподдерживаемый payload отклоняется |
| Module Data | Готовы scoped namespace, атомарная JSON-запись, версии, staging-миграции и rollback. БД/репозитории и экспорт продуктовых данных — этап 3 | Сброс/неудачная миграция тестового модуля не меняют данные соседнего; реальные истории Chat/Agent ещё не реализованы |
| Agent Gateway | Предстоит в 6.9: публичные операции задачи, статуса и отмены по ID с идентичностью пользователя и исходного модуля | Будущий Character использует те же права и подтверждения; готовая основа read-context не предоставляет Agent Control |

`ResourceEstimate` движка остаётся оценкой LLM. Дополнительные нужды аудио, памяти и рендера учитывает сервис ресурсов; Character не создаёт собственный конкурирующий планировщик моделей. Активные запросы Chat/Agent не вытесняются без политики общего планировщика. Владение микрофоном и передача его другому режиму должны быть явными.

События модуля — уведомления с проверенной схемой. Текст модели, воспоминания, `memory_candidates` и названия анимаций не становятся разрешением выполнить системную команду.

### Character Core и протокол

Профили Neutral/Friendly/Sarcastic/Strict/Curious и пользовательские профили содержат версионированные черты в диапазоне 0–1. Базовый профиль отделён от текущего состояния, настроек пользователя, явных границ и приобретённых поправок. Явные границы имеют приоритет; «серьёзно, прекрати шутить» не должно требовать удаления всего характера.

Emotional State — вычислительное состояние, не утверждение о субъективных переживаниях. Первичная и вторичная эмоции, интенсивности, переходы, ослабление и восстановление нейтрального состояния сохраняются между репликами. Расширяемый реестр состояний и анимаций принадлежит Character; одно выражение не привязывается к обязательной эмоции.

Версионированный сценарий ответа включает intent, состояние/эмоции, сегменты с ID и порядком, текст, интенсивность, голосовой стиль, анимацию и кандидаты памяти. JSON Schema ограничивает значения, длины и количество сегментов. Данные пользователя отделены от управляющих полей; стиль и анимация выбираются из возможностей адаптеров.

До реализации выбрать framing завершённых сегментов: отдельные проверяемые записи/события вместо попытки озвучить обрывок незавершённого JSON. Провайдер без строгой потоковой схемы использует буферизацию полного валидного ответа или текстовый fallback. Уже проигранный сегмент не воспроизводится повторно после исправления/повтора. Сбой схемы не исполняет непроверенную команду и не закрепляет кандидата памяти как факт.

Context Orchestrator собирает базовые инструкции, профиль, состояние, границы пользователя, задачу, последние сообщения и выбранную память с отдельными бюджетами токенов. При нехватке места сокращается менее важная память. Запись памяти и консолидация отделены от критического пути воспроизведения и ограничены очередью и временем работы.

Инициативные реакции используют события и активную задачу, настройку пользователя, ограничение частоты и бюджет запросов. После деактивации инициативных запросов нет; выбор любознательного профиля не открывает микрофон и не даёт агентных прав. В диагностике показываются короткие метки выбора состояния и использованные записи памяти, а не скрытые рассуждения модели.

### Голос, анимация и отмена

В обычном голосовом MVP сохраняются локальный STT и запись по нажатию. Постоянный VAD в Character действует только внутри явно включённого голосового сеанса; выключение Character и suspend останавливают микрофон. Раздельно настраивается передача текста и аудио внешним провайдерам.

Recognition/Speech adapters объявляют streaming, языки, голоса, эмоции, таймкоды, отмену и сведения о стоимости с источником и датой. Кандидаты из TZ — Gemini-TTS, ElevenLabs, OpenAI Speech/Realtime; выбор и реальные возможности требуют отдельной проверки. Их наличие в документе не является выбором поставщика или обещанием качества/цены.

Единственный Response Planner выдаёт одинаковую эмоциональную директиву TTS и Animation. Playback clock — основа синхронизации; при наличии используются таймкоды/фонемы/виземы, иначе допускается явно отмеченный приближённый режим по амплитуде. Недоступная эмоция преобразуется в поддерживаемый вариант с диагностикой, без заявления о точном совпадении.

Перебивание сначала аннулирует текущий `response_id`/поколение ответа, затем останавливает LLM, TTS, очередь аудио и связанные анимации. Поздние результаты отклоняются на каждом потребителе. Новый ответ получает новый ID. Аудиобуферы и очереди ограничены; фон консолидации не задерживает эту операцию.

Avatar/Character pack отделён от renderer и содержит разрешённые состояния, ресурсы и совместимые версии. Отсутствие аудио не останавливает idle и UI; отсутствие анимации оставляет текст/голос работоспособными. Выбор renderer зависит от решения 3.1, включая рассматриваемую Avalonia; TypeScript-примеры в TZ не предопределяют оболочку.

### Представление вне окна RAMVI и контекст приложений

Дополнение к Add-TZ вводит четыре режима: Embedded, Desktop Overlay, Companion Window и Application Assistant. Character worker, профиль, память, состояние и текущий ответ остаются одними и теми же при смене представления. Оконная часть — заменяемый адаптер; новая форма отображения не требует изменений Character Engine.

Главное окно, видимость аватара и активность модуля имеют отдельные состояния. Работа companion после закрытия главного окна допускается по явной настройке; полный выход останавливает worker, захват звука и синтез. При скрытом аватаре активный микрофон по-прежнему виден в общем индикаторе и доступен мгновенный Stop.

Для Overlay/Companion нужны перемещение, прозрачность, сворачивание, скрытие, временный click-through и способ вернуть управление без клика по самому прозрачному окну. Проверяются фокус, несколько мониторов, DPI и возврат скрытого/вынесенного за экран окна. Требования входят в сравнение оболочек 3.1; недоступная возможность OS обозначается как ограничение адаптера.

| Уровень | Контекст/действие | Граница |
|---|---|---|
| Screen | Изображение выбранного окна для image-capable LLM Provider | Только разрешённое окно; внешняя передача изображения — отдельное согласие; текстовый Engine не объявляется мультимодальным без поддержки |
| UI Context | Выделение, текст и доступные элементы через системный адаптер | Доступ чтения не даёт права нажимать/вводить; недоступные данные не выдумываются |
| Agent Control | Разрешённые нажатия, ввод, открытие и изменение данных | Выполняет Agent через обычный policy/подтверждения и журнал, не анимационный адаптер |

Публичный Context Provider предоставляет снимок с происхождением, приложением/окном, временем и ID. Контекст получают по запросу/событию, с ограничением частоты, размера и стоимости; постоянная отправка скриншотов в облако не включается. Если достаточно выделенного текста или структуры UI, изображение не требуется. Отзыв гранта останавливает сбор и новые отправки; данные контекста не становятся памятью или записью журнала по умолчанию.

Запрос «вот здесь неправильно, исправь» проходит определение разрешённой цели, получение контекста, уточнение при неоднозначности и передачу задачи Agent. Непосредственно перед действием Agent сверяет окно/элемент и актуальность снимка; смена фокуса или потеря разрешения останавливает действие. Character озвучивает результат по тому же каналу задач, не дублирует UI-автоматизацию и не получает Agent Control из факта доступа к Screen.

Общие контракты/гранты принадлежат платформе и доступны другим модулям. Представление, выбор реакции и сбор контекста для разговора принадлежат Character; системные адаптеры и агентные действия используют существующие сервисы/Agent. Чтение UI и обработка изображения не должны становиться обязательными зависимостями обычного Chat.

### Character Brain

Дополнение Add-TZ описывает двухступенчатую схему: основная LLM выдаёт описание события и контекста, а контроллер реакций выбирает стратегию, эмоцию, интенсивность и инициативу. Это внутренний версионируемый контракт Character (9.30–9.31), не новая обязательная подсистема Core. Оба сообщения проходят проверку схемы и границ значений; confidence требует проверки калибровки, а выход контроллера не расширяет разрешения пользователя.

Начать следует с параметрического контроллера и памяти, сохранив заменяемый интерфейс. Обучение во время работы в базовом варианте означает ограниченную адаптацию с историей и откатом. Для отдельной маленькой обучаемой сети сначала определяются данные, сигнал обратной связи, цель, бюджет, контрольная выборка и checkpoint; затем проводится сравнение с обычным контроллером, отключённым обучением и ленивой стратегией. Веса основной LLM и базовая личность автоматически не меняются. Маленькая сеть и human_brain являются разными необязательными адаптерами; ни один не обязателен для запуска модуля.

### Память и адаптация

Character хранит Working/Profile/Episodic/Semantic/Behavioral Memory и Character State раздельно по смыслу. Профили и текущее состояние сохраняются уже в текстовом прототипе; полноценный поиск и консолидация вводятся отдельной фазой Memory.

Запись памяти имеет ID, тип, предмет, значение, confidence, occurrences, first/last seen, статус и source IDs. Различаются слова пользователя, наблюдения, интерпретации и предположения. LLM предлагает кандидатов, правила модуля решают, что можно подтвердить. Противоречия сохраняются как противоречия, а не объединяются в новый «факт».

Поиск сочетает темы, сущности, актуальную задачу, значимость, частоту, давность и незавершённые события; semantic similarity — один из сигналов. Начальный SQLite использует индексы/FTS; embedding-индекс подключается через адаптер при необходимости. Весь журнал не перечитывается и не передаётся LLM на каждой реплике.

Просмотр, исправление, экспорт и удаление включают поисковые индексы, кэш и производные сводки. Политика забытого факта предотвращает его автоматическое восстановление из прежних source IDs. История изменений адаптации отделена от фактических воспоминаний.

Адаптация не меняет веса LLM и базовый профиль: корректируется ограниченная персональная поправка с заданной скоростью, уверенностью, историей и сбросом. Неоднозначная реакция не считается достоверным одобрением. Настройки и прямые границы пользователя выше приобретённых параметров.

## Приёмка и внедрение

Числа ниже — **цели и сценарии из TZ, не измеренные результаты RAMVI**: узнаваемость профиля после 100 реплик, целевые 60 FPS на CPU-рендере, начало озвучки до 1,5 с при подходящем провайдере/соединении и реакция на перебивание до 250 мс. Для замеров фиксируются модель, адаптер, железо, буферы, сеть и определения начала/конца события; публикуются распределение задержек, ошибки и память, не один удачный пример.

Приёмка включает:

- Отсутствующий пакет Character; установленный, но выключенный; активный текстовый режим; голос; деактивацию, suspend/resume и повторное включение. В неактивном состоянии нет его аудиозахвата, потоков синтеза, animation loop, фоновых задач и оставшихся подписок. Память/VRAM возвращаются к исходному состоянию с учётом измеренного шума.
- Все оконные представления, закрытие главного окна и полный выход, прозрачность/click-through, смену приложения/фокуса и немедленный отзыв каждого из трёх грантов.
- Сбой worker, потерю провайдера, неверную схему, поздние события, заполненные очереди, обновление/откат и удаление модуля. Chat/Agent и их данные продолжают работать.
- Второй тестовый модуль с другими данными и событиями, подключённый без изменения ядра; проверку зависимостей между пакетами.
- Характер, эмоции, юмор и неоднозначные RU/EN-ситуации на новых диалогах и перефразировках. Контроль «Yeah/Day/Bill» не зашивается в код или промпт как готовый ответ; используется и отдельный набор непоказанных сценариев.
- Заведомо решаемый эталон тестовой обвязки; сравнение с «всегда neutral», одним статичным промптом и отключёнными памятью/адаптацией. Повторные прогоны отделяют уместность реакции от наличия JSON-метки.
- Память после перезапуска и сотен сообщений, противоречия, отсутствие вымышленных воспоминаний, удаление и смену пользователя/персонажа/провайдера.
- Слепое сопоставление нескольких TTS по одинаковому русскому корпусу: ударения, паузы, ирония, сарказм, смешение языков и переключение эмоции. Без TTS/аватара обязателен текстовый путь.
- Регрессии обычного Chat/Agent/API и LLM-движка. Если меняется Engine, выполняется его существующий fp32/WIDE30-экзамен; результаты новых модулей учитываются отдельно от скорости decode.

Human_brain сравнивается на одинаковых скрытых сценариях с обычным LLM-контроллером и параметрическим Character с памятью. Учитываются качество, устойчивость, адаптация, ресурсы и ошибки. Эксперимент имеет отдельные зависимости и формат checkpoint; выключение полностью возвращает обычный контроллер. Преимущество допускается утверждать только по воспроизводимым данным.
