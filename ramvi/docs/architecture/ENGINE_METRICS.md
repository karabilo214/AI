# Метрики Engine — пункт 2.4

Все API генерации используют один снимок метрик: модуль `ramvi_engine.metrics`, сбор в `App._run`. Арифметика движка и прежние стандартные поля API не изменены.

## Где получить

- Python `App.run`: итоговое событие `end` содержит `metrics`.
- OpenAI chat/completions и completions: `ramvi_metrics` в обычном ответе и в завершающем SSE chunk, независимо от `stream_options.include_usage`.
- Anthropic messages: `ramvi_metrics` в обычном ответе; в потоке — в `message_delta` с итоговым usage.
- Ollama chat/generate: `ramvi_metrics` в обычном ответе и последней NDJSON-записи `done=true`.
- `GET /engine/metrics`: авторизованный снимок счётчиков, последней генерации, текущего размещения и lifecycle. Доступ использует обычный API-ключ сервера.

Текущий план в корне статуса относится к текущей модели. `metrics.last` — исторический снимок последней завершённой/остановленной генерации: после unload он сохраняется. Для проверки свежести есть `generation_id`, имя модели, `started_at_unix_s` и `finished_at_unix_s`. Тексты запроса/ответа и сообщения исключений в хранилище метрик не записываются.

В успешном потоке метрики передаются один раз, после окончания генерации; промежуточные части не выдают прежний снимок за новый. Метрики ошибок генерации прикрепляются к конкретному исключению и его JSON/stream error, без чтения глобального `last` другой генерации. Ошибки авторизации, синтаксиса и валидации до начала генерации не получают вымышленных метрик. При разрыве соединения итоговые метрики доступны в статусе, даже если отправить их клиенту уже невозможно.

## Время и токены

| Поле | Значение |
|---|---|
| `ttft_ms` | До первого непустого события text/reasoning или готового tool call в generation worker |
| `first_text_ms` | До первого непустого text; рассуждения отдельно не считаются текстом ответа |
| `engine_first_token_ms` | Время первого токена по счётчику native-движка |
| `prefill_ms`, `decode_ms` | Измеренные native-движком интервалы |
| `worker_total_ms` | Время работы генератора, включая ожидание модели и обработку выдачи |
| `input_tokens` | Полная длина входного запроса в токенах |
| `prefill_tokens` | Фактически обработанный native-движком суффикс с учётом KV-кэша |
| `output_tokens` | Число токенов, выданных native-генератором; включает EOS по существующему контракту usage |
| `decode_tokens` | `max(output_tokens - 1, 0)`, первый токен исключён |
| `decode_tokens_per_second` | `decode_tokens × 1000 / decode_ms` |

`timing_scope=generation_worker_including_model_wait`: это **не сетевой TTFT клиента**. Отсчёт начинается в worker, после HTTP-разбора, формирования prompt и подготовки constraint; учитывается ожидание модели. Пустая role-часть OpenAI не считается первым содержательным выводом. Сетевые задержки и время до запуска worker измеряются внешним клиентом. Для сравнения с существующими WIDE30/Ollama использовать их прежний клиентский протокол, не смешивать определения.

Интервалы измеряются монотонным `perf_counter`; Unix-время служит только для привязки снимков. Паузы/backpressure потребителя могут входить в worker_total; это не чистое время GPU. Дополнительная CUDA-синхронизация ради метрик не вводится. Если нет токенов, декодирования или знаменатель равен нулю, соответствующая скорость/TTFT — `null`, а не бесконечность или искусственный ноль. Токены не называются словами.

## Draft

`draft` содержит `drafted_tokens`, `accepted_tokens`, `acceptance_rate`, `calls`, `skips`, `probes`, `passes`, `single_steps`. Источник — stats native-движка. Доля принятия равна `accepted_tokens / drafted_tokens`; при отсутствии черновых токенов она `null`.

Это статистика выполненных проверок движка. При stop-последовательности/отмене проверенный batch может содержать токены, не попавшие в видимый пользователю текст. Доля принятия не равна ускорению; для вывода о скорости нужны сравнения на одинаковых запросах. Отсутствующие счётчики остаются `null`, не подменяются оценками.

## RAM и VRAM

- `ram_start_bytes`, `ram_end_bytes`, `peak_ram_bytes`, `ram_samples`: текущий process RSS (на Windows — working set), с выборкой по умолчанию каждые 50 мс и на границах генерации. `ram_scope=sampled_process_rss`. Короткие пики между выборками могут быть пропущены. Это не размер только весов и не lifetime high-water mark процесса.
- Источник RSS: Windows GetProcessMemoryInfo, Linux `/proc/self/statm`, macOS task_info. Недоступное измерение — `null`.
- `vram_start_allocated_bytes`, `vram_end_allocated_bytes`, `peak_vram_allocated_bytes`, `peak_vram_reserved_bytes`: PyTorch CUDA allocator устройства текущей модели, включая resident-веса/draft, постоянные и временные массивы. `vram_scope=process_device_allocator`.
- Счётчики пика сбрасываются после получения исключительного доступа к генерации, а не при поступлении конкурирующего HTTP-запроса. Доступ удерживается и для native App без EngineSession через reentrant lock.
- Значения относятся ко всему процессу на устройстве за интервал генерации, не к отдельному тензору или только текущему batch. Параллельная неуправляемая работа на том же устройстве мешает атрибуции; такой режим не обещается.
- `driver_memory_included=false`: служебная память CUDA/JIT и другие процессы не включены. Поведение после unload описано в [приёмке lifecycle](../reports/ENGINE_LIFECYCLE_ACCEPTANCE.md).

Sampler не вызывает CUDA в своём потоке, завершается при успехе, отмене, исключении и generator.close. Пустой/CPU-тестовый движок не инициирует CUDA ради метрик. При сбое CUDA probe выставляется `vram_probe_error`, неизвестные значения остаются `null`; ошибка счётчика не подменяется измеренным нулём. При отказе запуска RSS-потока остаются граничные выборки с `ram_sampler_error`.

## План и состояние

`plan.layers` копирует фактический `engine.place` в конце генерации, включая изменения после OOM/переразмещения; `counts` группирует режимы, `context_tokens` берётся из текущего движка. Это не устаревший стартовый `R` или оценочный ResourceEstimate.

Статус хранит ограниченные данные: число активных generation workers (включая ожидающие модель), счётчики `completed/error/cancelled/aborted` и один последний снимок. `aborted` означает закрытие генератора потребителем; оно не объявляется завершённым ответом. Ошибки содержат тип исключения, без его текста в самом снимке метрик. Несколько чтений статуса возвращают независимые копии; накопления истории диалогов нет.

`schema_version=1` относится к формату метрик. Общее версионирование API/событий остаётся пунктом 2.5.

## Проверка и ограничения

Контрактные тесты проверяют формулы на ручных числах, пустой вывод/неизвестные показатели, CUDA probe на контролируемом адаптере, остановку sampler, отмену/ошибки, повторные запросы, смену фактического плана, авторизацию и все пять API в stream/non-stream режимах. Числа тестового backend — фикстуры, не скорость реальной модели. Дополнительно локально проверены обычный и потоковый chat/messages через установленные официальные OpenAI/Anthropic SDK: namespaced-поле сохраняется и не нарушает разбор ответов.

Новых аппаратных измерений скорости или GPU-пика для этого пункта не проводилось. CUDA-вызовы проверены адаптером; это не аппаратная калибровка точности/накладных расходов. Рабочий RSS-путь проверен локально на macOS; Windows/Linux ветви требуют платформенной проверки при следующем необходимом запуске/CI. Отдельная GPU-машина только ради изменения формата метрик не использовалась.

Итог локальной проверки: 228 тестов и 125 подтестов в полной среде; 132 теста и 7 пропусков в лёгкой. Mypy проверил 31 файл, включая конфигурацию Windows; ruff и ссылки документации прошли. Совместимость SDK: 4 проверки, OpenAI 3.50.0 и Anthropic 2.8.0, все обращения направлены на локальный тестовый сервер. Это проверка контракта, не аппаратный бенчмарк.
