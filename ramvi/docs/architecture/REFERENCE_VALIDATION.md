# Эталонная проверка токенов и логитов — 2.7

`ramvi_engine.validation` и инструмент `check_reference` проверяют численные результаты по одинаковым ID входных токенов. Совпадение декодированного текста не заменяет сравнение логитов/argmax.

## Контракт

- `compare_logits`: конечные полные векторы одинаковой длины, `abs(error) <= atol + rtol * abs(reference)`, отдельное точное совпадение argmax. При равных логитах выбирается минимальный ID. Даже если изменение argmax уложилось в допуск, проверка не проходит.
- `compare_tokens`: точные ID, EOS и длина; лишний/потерянный суффикс считается расхождением.
- `TorchReference`: обычный torch float32 causal forward, исходные HF/GGUF веса слой за слоем, без native Engine kernels/repack/CpuMat. Выходная матрица вычисляется частями; TF32 выключается.
- GGUF использует независимый block decoder Q4_K/Q6_K/Q8_0/F16/F32/BF16. Нормировки, attention, router и эксперты считаются torch fp32. Для сопоставления с представленным native-кэшем GGUF K/V округляются в fp16; это отражено в отчёте. Эксперты MoE загружаются только по выбранным ID.
- Native GGUF сравнивается по реальному выходу head kernel. HF использует точную исходную выходную матрицу и native hidden state, отдельно проверяется выбранный bound-based head токен.
- HF дополнительно проверяется официальным Transformers eager fp32 при `--transformers`. Его расхождение влияет на общий результат проверки.

Диагностический JSON содержит rendered chat prompt, точные input IDs и их токены, thinking-mode, полный SHA256 весов, исходную конфигурацию, выбранные токены и top reference logits. Teacher-forced позиции используют один и тот же reference prefix в обеих реализациях; отдельно сохраняется свободная greedy-последовательность native. При `--trace` на расхождении сохраняются ошибки last-hidden после каждого доступного слоя. Этот путь предназначен для диагностики, не для измерения скорости.

Пример запуска из репозитория:

```sh
python -m ramvi.engine.tools.checks.check_reference --model Qwen3-0.6B --transformers --trace --case original --case echo_control --steps 2 --out results/reference.json
```

GGUF/MoE задаются локальным путём или именем уже установленной модели; для независимого контроля MoE можно указать `--resident 0`. `--thinking` включает штатный thinking-шаблон того же токенизатора. Без него сохраняется исходный non-thinking режим. Значения `--atol`/`--rtol` — заданные допуски, а не измеренные ошибки; отчёт сохраняет и допуски, и фактические отклонения. Неполный/прерванный отчёт имеет `complete=false`.

## Локальная диагностика исходного 2 + 2

Проверен официальный HF checkpoint Qwen/Qwen3-0.6B revision `c1899de289a04d12100db370d81485cdf75e47ca`. SHA256 `model.safetensors` — `f47f71177f32bcd101b7573ec9171e6a57f4f4d31148d38e382306f42996874b`, он совпал с опубликованным LFS SHA256. Сверены также tokenizer.json и отдельно скачанные config/generation_config/tokenizer_config на закреплённой revision. [Первичный источник метаданных](https://huggingface.co/api/models/Qwen/Qwen3-0.6B?blobs=true), [закреплённая конфигурация токенизатора](https://huggingface.co/Qwen/Qwen3-0.6B/resolve/c1899de289a04d12100db370d81485cdf75e47ca/tokenizer_config.json).

В macOS/CPU официальном Transformers eager fp32 на запрос `Reply with just the number: 2 + 2 =`, с `enable_thinking=False`, три повтора дали ID `[17, 151645]`: `2` и EOS. Независимый torch oracle выбрал тот же первый ID. Максимальное абсолютное отличие логитов в исходном запросе — `2.86102294921875e-05`; разрыв top-1/top-2 — `6.158317565917969`. Это не смена argmax из-за близких оценок.

Дополнительные измерения того же checkpoint:

| Контроль | Ответ Transformers eager fp32 |
|---|---|
| Английская перефразировка 2 + 2 | `2 + 2 = 4` |
| Русская перефразировка 2 + 2 | `Ответ: 4` |
| Свежий пример 211 × 37 | `211 × 37 = 7997`, неверно: эталон `7807` |
| Большое число 200003 + 41 | Вывод усечён лимитом 16 токенов; полный ответ не оценивался |

На этих дополнительных первых позициях oracle и Transformers выбрали одинаковые ID; максимальное абсолютное отличие логитов не превысило `3.4332275390625e-05`.

На **том же исходном вопросе** с `enable_thinking=True` greedy-генерация завершилась EOS за 129 токенов, итог после служебного thinking-раздела — `4`. Первые логиты также совпали с независимым oracle (максимальное абсолютное отличие `4.76837158203125e-05`). Измерения показывают зависимость ответа этого checkpoint от режима/формулировки. Они не доказывают общую арифметическую надёжность модели.

Эти данные локализуют HF ответ `2` до поведения официального checkpoint на конкретном non-thinking prompt. Сопоставление с native Windows/CUDA на **тех же SHA/ID** и самостоятельная проверка GGUF/MoE выполняются итоговым аппаратным прогоном. Результат для HF нельзя автоматически переносить на MoE или другой набор весов.

Сырые локальные свидетельства: `ramvi/results/reference_cpu_20261114/{original,ablation,thinking,provenance,upstream_model_info}.json` (исключены из Git). Проверки декодера включают ручные блоки, свежие случайные блоки, причинность tiny-сети, повторяемость и намеренно неправильную постоянную стратегию. Числа tiny-сети/контрольные допуски не являются замерами большой модели.

Для крупных GGUF независимые линейные проекции декодируют не более 1024 строк весов за раз, включая выходную проекцию. Это ограничивает рабочие массивы эталона; native inference не использует этот код. Проверка сравнивает блочный результат с полной матрицей на свежей случайной матрице и запрещает эталону запрашивать блок целиком. Частичный отчёт сохраняет активный случай и завершённые позиции до продолжения тяжёлой диагностики.

## Проверка шаблона Thinking-only GGUF

Совпадение native/oracle на одинаковых ID не проверяет правильность самого chat template. Поэтому диагностика дополнительно сравнивает установленный tokenizer template и встроенный GGUF template, сохраняет rendered prompt и ID. `--legacy-template` явно воспроизводит прежний шаблон только для диагностического сравнения. Он не меняет стандартный режим приложения.

В проверенном GGUF `qwen3:30b` метаданные называют Qwen3 30B A3B Thinking 2507. Его официальный [model card](https://huggingface.co/Qwen/Qwen3-30B-A3B-Thinking-2507) указывает поддержку только thinking. Общий soft-switch шаблон 8B принудительно закрывал reasoning, тогда как встроенный шаблон оставляет его открытым. Коррекция находится в `model_template.py`; сам prompt с вопросом и native математика не подменяются.

Для GGUF проверяемые позиции можно получить одним causal forward: сначала native предлагает короткую последовательность, затем независимый oracle считает полные логиты для каждого её префикса. Каждый предложенный ID обязан совпасть с argmax эталона; при всех совпадениях индукция даёт ту же greedy-последовательность. Дополнительно сравниваются native-выбор head, его полный вектор и повторная свободная native-генерация. Любое расхождение остаётся FAIL. Это убирает повторную деквантизацию всех весов для каждого токена. Причинность и равенство блочного/раздельного forward проверяются отдельно на свежих tiny-последовательностях.
