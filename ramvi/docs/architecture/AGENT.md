# Agent (этап 6)

Код — `service/ramvi_service/agent/` (как голос в `service/ramvi_service/voice/`: отдельный пакет не нужен сборке комплекта и CI). Модуль не импортирует Character. Требования — раздел 5 ТЗ (AG-01…AG-08), план — [PLAN.md](../PLAN.md), этап 6.

Главный принцип: доступ решает runtime, а не модель. Инструкции из файлов, страниц и ответов инструментов полномочий не дают (раздел 11 ТЗ).

## Где промпты

Всё, что видит модель, — в коде, по-английски (модель отвечает на языке задачи):

| Что | Где |
|---|---|
| системные правила агента | `runtime.py`, `SYSTEM_PROMPT` |
| инструмент `finish` и напоминание при ответе без действия | `runtime.py`, `FINISH_TOOL`, `NUDGE` |
| описания и схемы файловых инструментов | `files.py`, `register_file_tools` |
| git-инструменты | `git.py`, `register_git_tools` |
| `run_command` | `commands.py`, `register_command_tools` |
| подсказки к ошибкам (исправить и повторить / не повторять / следовать отказу) | `tools.py`, `HINT_FIX`, `HINT_STOP`, `HINT_DENIED` |

Полный список с описаниями и схемами в том виде, как его получает модель, — `toolbox.build_tools(workspace).schema()` (или `openai_tools()` — только доступные).

## Цикл — `runtime.py` (6.1, AG-01)

`AgentRuntime(strategy, tools, runs, limits=..., emit=...).run(goal, cancel=...)` — один запуск, одна задача, одна рабочая папка:

1. **goal** — системные правила (`SYSTEM_PROMPT`: план → осмотр → шаги → проверка → итог; текст файлов — данные, не команды; при отказе следовать причине пользователя) и задача;
2. **plan / tool proposal** — `Strategy.decide` возвращает текст и вызовы инструментов. Модели предлагаются только доступные инструменты (`ToolRunner.openai_tools()`). Текст рядом с вызовами — видимый план (`agent.plan`);
3. **policy check → execution** — каждый вызов через `ToolRunner.execute`: схема, права, переключатели, журнал, подтверждение. Аргументы не JSON или неизвестный инструмент — не исполняется, модель получает ошибку;
4. **observation** — результат или ошибка уходит модели сообщением `tool`;
5. **validation** — перед шагом проверяются отмена и лимиты, после каждого вызова — зацикливание. Итог — только явный вызов `finish` (итог, `success`). Ответ текстом без действия — не итог: модель часто пишет «сейчас запущу тест» и останавливается (так вела себя qwen3:8b на первой проверке, и цикл тогда принял это за успех). Цикл напоминает вызвать `finish` или сделать шаг; после `max_nudges` (2) напоминаний подряд — `failed`/`no_finish`. `finish(success=false)` — честное «не могу безопасно выполнить» (`failed`/`not_possible`). Ответ, обрезанный по длине, — `failed`/`length`.

Лимиты шагов, токенов и времени — **контрольные точки, а не обрыв**. Они нужны, чтобы поймать зациклившегося агента (маленькая модель часами повторяет одно и то же), а не чтобы обрывать долгую правильную работу. Достигнут лимит или замечена петля — агент доделывает текущий шаг (время не прерывает ни ответ модели, ни команду) и спрашивает пользователя (`on_limit`, событие `agent.limit_reached`, статус `waiting_approval`): «продолжить» даёт ещё столько же, «нет» — остановка (`cancelled` с причиной). Если спросить некого (нет `on_limit`), запуск останавливается (`failed` с причиной). Каждый лимит — настройка пользователя на вкладке «Агент», `None` — без ограничения. Немедленно останавливает только Stop пользователя.

| Контрольная точка (`RunLimits`) | По умолчанию | Причина |
|---|---|---|
| `max_steps` | 50 | `max_steps` |
| `max_tokens` (prompt + completion за запуск) | 1 000 000 | `max_tokens` |
| `max_duration` | 3600 с | `max_duration` |
| `max_same_lines` — правок одних и тех же строк файла | 3 | `stuck` (`same_lines: файл:строка`) |
| возврат файла к виду, который уже был в запуске | всегда, если проверка петель включена | `stuck` (`oscillation: файл`) |
| `max_no_progress` — тот же вызов с тем же результатом без изменений файлов между ними, подряд | 3 | `stuck` (`no_progress: инструмент`) |

Зацикливание распознаётся по журналу запуска (`progress.py`), а не по одинаковым вызовам: перечитать файл после своей правки — нормально (запись или команда между вызовами — уже новое состояние). Для этого результат применённой записи несёт `applied`: файлы, хеши до/после и номера изменённых строк (из diff). `max_calls_per_step` (20) — не остановка: лишние вызовы шага получают `agent.run.too_many_calls`, модель повторит их следующим шагом. Тайм-аут одной команды — `ToolAccess.command_timeout` (600 с, `None` — без ограничения); модель может попросить меньше, но не больше.

Остальные причины: `done`, `cancelled` (Stop пользователя или «остановить» в подтверждении), `model_error`, `length`, `no_finish`, `not_possible`. Статус запуска (`running` → `waiting_approval` на время вопроса → `done`/`failed`/`cancelled`), шаги, токены, итог и причина пишутся в `agent_runs` (поля `result`, `stop_reason` — миграция v3); вызовы — в `tool_calls`.

События (`emit`): `agent.step`, `agent.plan`, `agent.tool_call`, `agent.tool_approval_required` (с diff или командой), `agent.tool_result` (с `change_id`), `agent.limit_reached`, `agent.message`, `agent.done`. У каждого — `run_id`, `seq`, монотонное `ts`, `version`.

`LLMStrategy(complete)` — MVP-стратегия: OpenAI-совместимый запрос (`tools`, `temperature: 0`, `max_tokens`) к основной модели; `complete` — обёртка над `SharedLLM.complete` (общая очередь и отмена). Стратегия отделена от исполнения и безопасности: другую (6.8) можно подключить, не трогая инструменты, права и подтверждения.

Тесты: `tests/test_agent_runtime.py`, `test_agent_progress.py` (модель — сценарий, инструменты, журнал, подтверждения и хранилище — настоящие).

## Границы доступа — `workspace.py` (6.3, AG-03)

`Workspace(root, Permissions(...), Restrictions(...))` — явный grant папки, которую выбрал пользователь. Корень приводится к реальному пути (symlink на папку допустим только в самом выборе пользователя).

**Ограничения ниже — по умолчанию.** Пользователь вправе снять любое из них, вплоть до полного доступа: это его компьютер, и запрещать ему мы не можем. Снимает ограничения только пользователь — в «Настройки» → вкладка «Агент»; у модели и инструментов такого пути нет. Вкладка появляется динамически, только если модуль Agent установлен (вкладки модулей — `SettingsViewModel.AddTab`).

| Настройка | По умолчанию | Если снять |
|---|---|---|
| `Permissions.read / write / terminal / network` | только `read` | `Permissions.full()` — все права |
| `Restrictions.confine_to_root` | да | любые пути (абсолютные, `..`), ссылки открываются как обычно |
| `Restrictions.secret_patterns` | список ниже | пустой набор — секреты доступны |
| `Restrictions.protect_git` | да | запись в `.git` разрешена |
| `Restrictions.safe_git` | да | git-инструменты работают и с репозиторием, чьи настройки могут запустить программу |
| `ToolAccess.disabled` | все включены | выключенный опасный инструмент не предлагается модели и не исполняется |
| `ToolAccess.allow_destructive_commands` | нет | разрушительные команды можно предлагать (каждая всё равно с подтверждением) |
| `ToolAccess.confirm_writes` / `confirm_commands` | да | запись / команда применяется без вопроса (журнал: `auto`) |
| `ToolAccess.confirm_destructive` | да | разрушительная команда не спрашивается отдельно, в том числе внутри серии |
| `ToolAccess.max_series` | 20 | сколько следующих действий можно разрешить одним подтверждением |
| `ToolAccess.command_timeout` | 600 с | предел одной команды; `None` — без ограничения (остановит только Stop) |

`Restrictions.none()` снимает все ограничения путей. Права и ограничения путей независимы: полный доступ к путям не даёт права записи и наоборот.

При ограничениях по умолчанию каждый путь от модели проходит `Workspace.resolve(path, permission=..., must_exist=...)`:

| Проверка | Ключ отказа |
|---|---|
| абсолютный путь, диск Windows (`C:`, `\\server`) | `agent.access.absolute` |
| компонент `..` (даже если остаётся внутри) | `agent.access.parent` |
| имя из точек/пробелов, `:` (потоки NTFS), `CON`/`NUL`/…, `\0` | `agent.access.invalid` |
| любой компонент — symlink, junction, точка повторного разбора | `agent.access.symlink` |
| реальный путь вне корня (запасная проверка) | `agent.access.outside` |
| обычный файл с несколькими жёсткими ссылками | `agent.access.hardlink` |
| секрет на любой глубине (`.env*`, `*.pem`, `*.key`, `id_rsa*`, `.ssh`, `.aws` …; без учёта регистра и хвостовых точек) | `agent.access.secret` |
| запись внутрь `.git` (хуки — исполнение кода) | `agent.access.git_write` |
| нет нужного права или grant отозван | `agent.access.permission`, `agent.access.revoked` |

Право `write` означает «можно предлагать запись»; сама запись всё равно идёт через diff и подтверждение (6.4). `revoke()` действует сразу на все следующие вызовы.

`open_read(path)` открывает только обычный файл (`O_NOFOLLOW`, где есть) и сверяет устройство и inode открытого файла с проверенным: подмену файла между проверкой и открытием прочитать нельзя. Подмена промежуточной папки в этот короткий промежуток не исключена — для локального однопользовательского приложения это принятый остаток риска; более строгая изоляция — sandbox этапа 8.

Тесты: `tests/test_agent_workspace.py`.

## Инструменты — `tools.py`, `files.py`, `git.py`, `commands.py` (6.2, AG-02)

Схема — `ramvi.agent.tools/1` (`ToolRunner.schema()`): у каждого инструмента имя, версия, нужное право (`read`/`write`/`terminal`/`network`), эффект (`read`/`write`/`command`), риск (`low`…`critical`) и JSON Schema аргументов с `additionalProperties: false`. Полный набор собирает `toolbox.build_tools(workspace, access)`.

**Опасные инструменты — в настройках доступа.** Инструменты с риском `high`/`critical` (`write_file`, `edit_file`, `apply_patch`, `run_command`) — переключатели на вкладке «Агент» (`ToolAccess.disabled`). Модели (`ToolRunner.openai_tools()`) предлагается инструмент, только если он включён, его право выдано и grant не отозван; по умолчанию права записи и терминала нет, поэтому предлагаются только инструменты чтения. Вызов выключенного инструмента или без права не исполняется (`agent.tool.disabled`, `agent.access.permission`) и попадает в журнал как `denied`.

`ToolRunner.execute(name, args, journal)` — единственный путь исполнения:

1. неизвестный инструмент или аргументы не по схеме — вызов **не исполняется**, в журнал попадает как `denied`, модели уходит `ERROR agent.tool.unknown` / `agent.tool.invalid_args` со списком ошибок;
2. вызов записывается в журнал **до** исполнения (`Journal.begin`); если записать не удалось — не исполняется;
3. результат или ошибка (`AccessDenied`, `ToolError`, любое исключение — без текста, чтобы не утекли пути) становятся `ToolResult` и дописываются в журнал (`Journal.finish`: ok, ключ ошибки, первые 4000 символов, длительность). Модель видит до 16 000 символов.

Журнал в базе — `StorageJournal` (таблица `tool_calls`, `AgentRuns.finish_tool_call`). Аргументы очищаются (`redact`): ключи вида `password`/`token`/`api_key` скрыты, текст длиннее 2000 символов заменён длиной, хешем и началом.

| Инструмент | Право | Что делает | Лимиты (`FileLimits`) |
|---|---|---|---|
| `list_dir` | read | содержимое папки; `d`/`f`/`l` (ссылка не раскрывается) | 500 записей |
| `read_file` | read | текст с номерами строк, по страницам | 1 МБ, 2000 строк за раз |
| `find_files` | read | поиск по маске имени или пути | 200 результатов, 20 000 файлов обхода |
| `grep` | read | регулярное выражение по текстовым файлам | 500 совпадений, 1 МБ на файл, 32 МБ всего, шаблон 500 символов |
| `diff` | read | unified diff двух файлов | 1 МБ на файл |
| `file_info` | read | тип, размер, время изменения (UTC), права, доступность записи | — |
| `git_status` | read | изменённые, добавленные, неотслеживаемые файлы | 30 с, 512 КБ |
| `git_diff` | read | текущие изменения (`staged`, `stat_only`) | 30 с, 512 КБ |
| `git_log` | read | история: хеш, дата, автор, тема (до 200) | 30 с, 512 КБ |
| `write_file` | write, high | **предложение**: новый файл или замена | 1 МБ |
| `edit_file` | write, high | **предложение**: замена одного уникального фрагмента | 1 МБ |
| `apply_patch` | write, high | **предложение**: несколько правок в одном или разных файлах, новые файлы; применяется целиком или никак | 50 правок, 1 МБ на файл |
| `run_command` | terminal, critical | **предложение** команды: тесты, линтеры, сборка, диагностика | до 600 с, 64 КБ на поток |

Обход (`find_files`, `grep`) не идёт по ссылкам, пропускает `.git` и секреты; бинарные, большие и недоступные файлы пропускаются и считаются в выводе. Каждый файл открывается через `Workspace.open_read`, поэтому все проверки 6.3 действуют и здесь.

Инструменты записи файлы **не меняют**: они возвращают `WriteProposal` (путь, хеш исходного файла, полное новое содержимое, diff) или `PatchProposal` (несколько записей и общий diff); любая ошибка в одной правке отменяет весь патч. Переводы строк и BOM сохраняются. Применение после подтверждения, снимки и откат — 6.4.

### git (`git.py`)

Git умеет запускать программы из настроек репозитория (fsmonitor, фильтры, внешний diff, textconv, хуки). Чтобы чужой репозиторий не получил так исполнение кода: системные и пользовательские настройки git отключены, fsmonitor/хуки/внешний diff/textconv выключены в командной строке, переменные `GIT_*` не наследуются, индекс не перезаписывается. Если в настройках репозитория есть `filter.*`, `include*` или `core.worktree`, инструмент отказывает (`agent.tool.git_unsafe_config`), пока пользователь не снял `Restrictions.safe_git`. Тест проверяет на настоящем git: обычный `git status` запускает программу из `core.fsmonitor`, наш — нет.

Пути в выводе — от корня рабочей папки; вывод ограничен выбранной папкой, секреты исключены pathspec-ами.

### Команды (`commands.py`, `process.py`)

`run_command` команду **не запускает**: разбирает (без оболочки — `&&`, `|`, `>` отклоняются, `agent.tool.shell_syntax`), находит программу (в PATH, полным путём или внутри папки) и возвращает `CommandProposal`. Запуск — `execute_command(proposal)` после подтверждения.

Разбор назначения — подсказка и блокировка очевидного, **не изоляция**: команда работает с правами пользователя, поэтому право `terminal` по умолчанию выключено и каждая команда идёт с подтверждением. Разрушительные (удаление и перемещение файлов, `git push`/`reset --hard`/`clean`/`branch -D`…, `sudo`, форматирование, оболочки и `python -c`/`node -e` — произвольный код) заблокированы (`agent.tool.destructive_blocked`), пока пользователь не включил `allow_destructive_commands`. Сетевые (`curl`, `git fetch`, `pip install`, `npm install`…) требуют права `network`. Переменные окружения с секретами (`*TOKEN*`, `*API_KEY*`, `*PASSWORD*`…) в процесс не передаются.

`process.run_process` (6.5, AG-05): без оболочки, stdin пуст, отдельная группа процессов (POSIX) или Job Object (Windows, механизм supervisor движка). По окончанию, тайм-ауту или отмене убивается всё дерево, включая оставшихся фоновых потомков; вывод читается до конца, хранится до лимита (`truncated`). Модели возвращаются код выхода, stdout и stderr.

Тесты: `tests/test_agent_tools.py`, `test_agent_git.py`, `test_agent_commands.py`, `test_agent_process.py`.

## Подтверждение и откат — `approval.py`, `changes.py` (6.4, AG-04)

Инструменты записи и команд возвращают предложение. Если `ToolRunner` создан с `ApprovalGate`, предложение после записи в журнал идёт в `ApprovalGate.handle`:

1. подтверждение выключено пользователем — применяется сразу (журнал `auto`);
2. действует разрешённая серия — применяется (журнал `approved`), остаток уменьшается;
3. иначе пользователю показывается `ApprovalRequest` — diff всех файлов или команда с папкой, признаками «разрушительная» и «сеть» — и запуск ждёт решения:
   - `approve` — применить; `series=N` — ещё N следующих действий того же вида без вопроса (не больше `max_series`); разрушительная команда спрашивается всегда, пока не выключен `confirm_destructive`;
   - `deny` с причиной — не применять; причина (поправка задачи) уходит модели (`agent.approval.denied`);
   - `stop` — не применять; `ToolRunner` отмечает журнал и поднимает `StopRequested`. Отменённый запуск (`cancel`) не спрашивает и не применяет.

Без решения `approve` (или явно выключенного подтверждения) рабочая папка не меняется.

`ChangeStore.apply` применяет запись или патч только целиком: пути заново проходят `Workspace.resolve` (отзыв grant во время ожидания — отказ), каждый файл сверяется с хешем, который видел агент (изменён после предложения — `agent.change.conflict`, правка пользователя не перетирается), снимки исходников и `manifest.json` пишутся **до** первой записи, запись атомарная (временный файл, fsync, `os.replace`), права файла сохраняются; ошибка на любом файле возвращает уже записанные и убирает созданные папки. Модели возвращается номер изменения, он же — в журнале (`change_id`).

`ChangeStore.rollback(id)` — действие пользователя (права агента не нужны, границы путей те же): файлы возвращаются из снимков, созданные удаляются вместе с пустыми созданными папками. Если файл после изменения поменяли ещё раз, откат отказывает (`agent.change.conflict`) до `force=True`. Снимки хранятся в папке данных и переживают перезапуск. Команды снимков не имеют: что меняет команда, заранее неизвестно — поэтому каждая команда требует подтверждения.

Окно подтверждения и история изменений с кнопкой «Откатить» — на экране агента.

Тесты: `tests/test_agent_approval.py`.

### Проверка на настоящей модели (6.1)

Ноутбук: Ryzen 7 260, RTX 5060 Laptop 8 ГБ, RAM 16 ГБ; RAMVI Engine из переносимого комплекта, `qwen3:8b` (GGUF Ollama), `--maxt 8192`, температура 0; подтверждения даёт скрипт, каждое записывается. Три разные задачи; для каждой сначала заведомо решаемая проверка (правильное решение проходит тест, исходный код — нет), после агента — независимый запуск тестов и проверка, что файлы тестов не тронуты.

| Задача | Итог агента | Шагов | Время | Независимый тест |
|---|---|---|---|---|
| ошибка в `average` | done | 6 | 23,5 с | проходит |
| ошибка в `clamp` | done (плюс одна лишняя безвредная правка `average`) | 8 | 13,9 с | проходит |

Что нашла проверка: (1) ответ текстом без действия принимался за итог — исправлено явным `finish`; (2) модель искала текст инструментом поиска по именам файлов — уточнены описания `find_files`/`grep`, а до этого проверка зацикливания остановила агента после трёх одинаковых результатов; (3) при контексте движка по умолчанию (2048) схемы инструментов и правила занимают почти всё и ответ обрезается — агенту нужен контекст не меньше 8192 (проверка — в 6.6).

## Готовность модели и качество вызовов — `readiness.py` (6.6, AG-06)

До первого запроса `AgentRuntime.run(goal, facts=ModelFacts(...))` проверяет модель (`facts_from_fit` берёт факты из оценки модели `ModelFit.for_file` и карты возможностей движка):

| Проверка | Итог |
|---|---|
| вызовы инструментов не поддержаны для модели | ошибка `agent.ready.no_tools` — агент не запускается |
| предел контекста модели меньше нужного | ошибка `agent.ready.model_context` |
| контекст профиля задачи меньше нужного | ошибка `agent.ready.context` (поднимается в профиле задачи) |
| модель меньше 7 млрд параметров | предупреждение `agent.ready.small_model`: может плохо планировать действия |

Нужный контекст считается по настоящему размеру правил и схем доступных инструментов (≈ 3 символа на токен) плюс 4096 на ответ и файлы: сейчас ≈ 6500 при всех правах — меньше 8192 режима задачи `agent`, больше 2048, при котором на проверке 6.1 ответ обрезался. Ошибки — запуск сразу `failed`/`model_not_ready` без обращения к модели; предупреждения — событие `agent.readiness` для интерфейса.

Некорректный вызов не исполняется (схема, неизвестный инструмент, аргументы не JSON — 6.2). Повтор имеет смысл только при исправимой ошибке: к ошибке добавляется подсказка — «исправь и повтори» (неверные аргументы, текст для замены не найден, файл изменился…), «не повторяй: другой путь или `finish(success=false)`» (запрет, секрет, выключенный инструмент, разрушительная команда) или «следуй причине отказа» (отказ пользователя). Неверные вызовы подряд (`max_invalid_calls`, 3) — контрольная точка `invalid_calls`. О невозможности безопасно выполнить задачу агент сообщает `finish(success=false)` (`not_possible`).
