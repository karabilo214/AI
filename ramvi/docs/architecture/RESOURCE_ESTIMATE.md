# ResourceEstimate — общий контракт оценки памяти

Пункт 2.2 плана. Реализация: `ramvi_engine.planning.resources`, без зависимостей от torch/numpy/CUDA. Используется в отчётах `make_plan` и `plan_gguf`, а также в общем примитиве предварительного подбора `assess_candidates`. Каталог моделей и его UI остаются этапом 4.

## Представление

Неизменяемый `MemoryUsage` разделяет байты на:

- `vram`: массивы на GPU;
- `ram`: собственные массивы в RAM, включая host-копии для подкачки;
- `mapped`: желательный рабочий набор файловых страниц, а не дополнительная malloc-копия и не размер всего файла на диске.

Проверка RAM консервативно складывает `ram + mapped`: нехватка файлового working set может не помешать загрузке, но вызвать чтение с диска. Общий mapped-файл нескольких моделей ОС может разделять; автоматический вычет общих страниц не выполняется.

`ResourceEstimate` содержит семь непересекающихся по назначению категорий:

| Категория | Что учитывается |
|---|---|
| `weights` | Resident-матрицы и выходная голова GPU; embedding/head и CPU-матрицы, читаемые из файла |
| `kv` | Все K/V, включая отдельные CPU и GPU копии hybrid и общий HF staging KV |
| `persistent` | Нормировки, позиции, RoPE, батчевые массивы/логиты, host staging; дополнительные CPU масштабы и распакованные F16/F32 матрицы GGUF |
| `streaming` | Два GPU-слота подкачки, packed host-копии; HF BF16 staging для CPU-слоёв |
| `cpu_workspace` | Приблизительный рабочий набор временных массивов CPU на одну исполняемую пачку, а не на каждый последовательный слой |
| `draft` | Отдельно переданная полная оценка draft, включая её веса, KV и буферы |
| `reserve` | Явный дополнительный запас; не считается выделенной памятью |

`allocated` суммирует категории без reserve; `required` добавляет reserve. Это оценки, а не сведения CUDA allocator. `to_dict()` возвращает JSON-совместимые данные с `schema_version=1`, `unit=bytes`, `kind=estimate`, компонентами, итогами и оговорками. Недопустимы отрицательные, дробные и boolean-значения байт.

## Формулы и размещение

Объём KV на слой: `2 × heads_kv × context_tokens × head_dim × bytes_per_element`. У HF GPU/CPU KV fp32; у GGUF GPU KV fp16, CPU KV хранится fp32 даже при округлении значений до fp16. `hyb` имеет обе копии. CPU-only у движка не появляется от наличия такой оценки.

HF-матрицы: прежняя приблизительная оценка `1.505 × elements` для lossless compression, с округлением вверх. Частота исключений зависит от весов; точность этой оценки не гарантирована. CPU читает BF16 из mmap. Общая embedding/head при tied weights учитывается один раз, независимая выходная голова — отдельно.

GGUF GPU оценивается по repack, а не только по размеру файла: Q4_K расширяется с 144 до 148 байт на блок 256 элементов; Q6_K — 210. Для packed-буферов каждый компонент выровнен до 256 байт, как в `_pack`. Слоты подкачки используют максимум каждого вида матрицы среди stream/hybrid слоёв, затем удваиваются. CPU дополнительные масштабы Q4_K/Q6_K занимают 64 байта на 256 элементов. Неквантованные CPU-матрицы имеют отдельную fp32-копию.

MoE оценивается отдельно: только CPU/GPU размещение, router, активные эксперты и их рабочие массивы. Подкачка/hybrid MoE отклоняются, неизвестные архитектуры/типы GPU-матриц не получают нулевую оценку.

## Общий путь для планировщика и подбора

```python
from ramvi_engine.planning.resources import MemoryUsage, estimate_hf, assess_candidates

# ck — метаданные модели; place — выбранное размещение.
main = estimate_hf(
    ck,
    place,
    maxt=4096,
    draft=draft_estimate.allocated,
    reserve=MemoryUsage(vram=reserve_gpu_bytes, ram=reserve_ram_bytes),
)
result = assess_candidates(
    {"candidate": main},
    vram_available=free_gpu_bytes,
    ram_available=available_ram_bytes,
)
```

Для GGUF — `estimate_gguf(g, place, maxt, ...)`: используются метаданные и raw-view тензоров, веса не распаковываются и не копируются на GPU. У main/draft должен быть согласованный контекст и batch. Общий запас задаётся один раз; если передать `draft_estimate.required`, его индивидуальный запас уже входит в draft и повторно добавлять его нельзя.

Оба планировщика возвращают новые поля `resources` и `resource_fit`. Поля старого плана сохранены: например, `ram_need` означает только прежнюю оценку RAM под слои, а не полный бюджет. Для интерфейса и подбора использовать `resources.required`. `resource_fit` совпадает с результатом `assess_candidates` при одинаковых бюджетах; включает дефицит VRAM/RAM и `guaranteed=false`.

В этом пункте оценка добавлена **после выбора размещения**. Прежняя политика выбора resident/CPU/stream и runtime-autofit GGUF не заменяются: автоматический выбор на основе полного бюджета, прогрев, OOM-откат и фактический план относятся к 2.6. Даже принудительный план, превышающий бюджет, возвращает честный отрицательный `resource_fit`; HF дополнительно выдаёт предупреждение. Оценка не запускает модель и не делает ручной план допустимым на неподходящем железе.

## Границы точности

Не учтены точно: временные пики загрузки/конвертации весов и выходной головы, CUDA context/allocator, JIT, xgrammar, CUDA-графы и их пулы, sampling временные массивы, многопоточность native-ядер, долгий блочный prefill, округление/фрагментация pinned Arena. Параметр batch относится к постоянным/CPU массивам, а не означает настройку размера пачки движка. Эти расходы требуют явного резерва и последующей калибровки на реальном оборудовании. RAM, возвращённая `ram_info()` на Mac, тоже является приблизительной.

Не заявляется гарантированное вмещение или ускорение. Проверки этого пункта используют ручные суммы, контролируемые метаданные, различные размещения/контексты/batch, повторяемость и равенство оценки планировщика и подбора. Новых аппаратных замеров не проводилось.
