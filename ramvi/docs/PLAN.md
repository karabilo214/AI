# RAMVI — план выполнения

Основание: техническое задание [RAMVI_technical_spec_v1.pdf](spec/RAMVI_technical_spec_v1.pdf) / [DOCX](spec/RAMVI_technical_spec_v1.docx) (редакция 1.0). Идентификаторы требований (UI-01, ENG-03 …) — из ТЗ; там же критерии приёмки.

Дополнение: [Character TZ](spec/Character-Module/TZ.md) и [архитектурные уточнения Character Module](spec/Character-Module/Add-TZ.md). В вопросах границ модуля уточнения имеют приоритет. [Подробный план модульности и внедрения Character](architecture/MODULES_AND_CHARACTER_PLAN.md) содержит зависимости, контракты и соответствие разделам ТЗ. Основа модульной платформы уже реализована в `ramvi/service/ramvi_service`: манифесты и Module Host, Scoped Services, события, аренды ресурсов, LLM Provider, изолированные workers и optional Context Provider. [Принятое решение модульной платформы](adr/ADR-0002-module-platform.md) и [контракт основы](architecture/MODULE_CORE.md) описывают границы готового кода. Полный Storage, UI, продуктовые Chat/Agent и Character остаются работами следующих этапов. Статус приёмки каждого пункта определяется его отметкой ниже; наличие контракта не означает готовность функционального модуля.

Отметка `[x]` ставится только после выполнения критерия «Проверка» данного пункта. Частично сделанное остаётся `[ ]` с пометкой в скобках, что осталось.

## Принятые решения

- [x] Название: приложение — **RAMVI**, движок — **RAMVI Engine**.
- [x] Расположение: каталог `ramvi/` в репозитории MyAI; всё, что относится к продукту, — только внутри него.
- [x] Движок `llm_app` переносится в `ramvi/engine/` и раскладывается по подпакетам (этап 1), без переписывания алгоритмов.
- [x] Оболочка: **Avalonia + C#** (.NET 10, self-contained single-file) — [ADR-0003](adr/ADR-0003-desktop-shell.md). Tauri + Vue/TypeScript из ТЗ отклонён: без WebView2 Runtime не запускается, а пользователь не должен ставить дополнительные программы.
- [x] Голос: **whisper.cpp + large-v3-turbo q5_0** локально по умолчанию, по выбору — сторонний API (`/v1/audio/transcriptions`, Google позже) — [ADR-0004](adr/ADR-0004-stt-backend.md).
- [x] Лицензия: MIT (пересмотр возможен до публичной беты). Файл `LICENSE` — в пункте 1.3, правообладатель: `Copyright (c) 2026 karabin`.

RAMVI остаётся платформой: Chat, Agent и необязательный Character — независимые функциональные модули. RAMVI Core в этом плане означает координацию приложения в сервисе; `ramvi_engine.core` остаётся вычислительным ядром. Характер, эмоции, память персонажа, адаптация и управление его голосом/анимацией принадлежат Character. Новые модули должны подключаться по общему контракту, без добавления специфической логики в ядро.

## Правила проекта

Действуют для каждого пункта плана.

1. **Структура.** Один модуль — одна ответственность. Код продукта — в пакетах; проверки — в `tests/`; замеры — в `tools/bench/`; разовые эксперименты в продукт не попадают.
2. **Без личного.** В коде, конфигурации, документах и истории git нет имён, адресов, имён машин, личных путей (`C:\…`, `/Users/…`), ключей. Пути — из настроек и переменных окружения, по умолчанию — в папке данных приложения.
3. **Результаты замеров** (json, логи) в git не попадают; в документах — только сводные цифры с указанием модели, железа и команды запуска.
4. **Строки интерфейса** — в ресурсах локализации (ru, en), не в коде.
5. **Стиль.** Python 3.12: `ruff` (lint + format), `mypy` для новых пакетов, docstring у публичных классов и функций. C# (оболочка, ADR-0003): nullable, предупреждения как ошибки, `dotnet format` — точные правила задаёт первый пункт с кодом оболочки. Имена — по-английски; комментарии и документация — по-русски.
6. **Готовность пункта.** Код + тесты + обновлённая документация; все тесты проходят; для изменений движка — экзамен скорости и точности (пункт 1.9) без ухудшения.
7. **Коммиты** — по одному логическому изменению, сообщение по-русски, в повелительном наклонении («Добавить …», «Исправить …»).

8. **Модульность.** Нет прямых зависимостей Chat → Character или Agent → Character. Модули используют публичные контракты сервиса; отключённый модуль не загружает тяжёлые зависимости, не захватывает устройства и не оставляет фоновые задачи. Форматы событий и данных версионируются, ресурсы и настройки имеют владельца модуля. Смена API требует доказанной необходимости и совместимого перехода.

# Tests before Relise
### Как правильно сравнивать Ollama и RAMVI
- **Параметр**   	**Требование**
- Модель	Идентичные веса, архитектура и квантование
- Вопросы	Одинаковые 100 вопросов в одинаковом порядке
- Контекст	Каждый независимый вопрос — в новой чистой сессии
- Chat template	Штатный для модели, одинаковая семантика ролей
- Thinking	Одинаковый режим
- Температура	Одинаковая, желательно 0 для воспроизводимости
- Генерация	Одинаковые ограничения и параметры
- Оборудование	Один ASUS, одинаковые условия нагрузки
- Время	Отдельно до первого токена и до полного ответа
- Результат	Полный текст, ошибки, число входных и выходных токенов

**Важное уточнение:** даже при температуре 0 не гарантируется побайтовое совпадение ответов. А для сравнения производительности нужно учитывать, что Ollama и RAMVI могут по-разному использовать GPU и CPU.

Я бы разделил 100 вопросов так
- Лёгкие — 30

Арифметика, факты, простые инструкции, форматирование
- Средние — 40

Логика, многошаговые задачи, анализ текста, программирование
- Сложные — 30

Многоэтапное рассуждение, сложный код, поиск противоречий

Для каждого вопроса я бы сохранял ещё и эталонный критерий правильности, независимо от ответов обоих движков. Иначе можно получить ситуацию, когда Ollama ошиблась, RAMVI повторил её ошибку, а сравнительный тест признал результат успешным.

## Самое важное — две отдельные оценки
### Качество:
- Правильность ответа.
- Выполнение инструкции.
- Полнота.
- Галлюцинации.
- Ошибки шаблона или thinking.
- Смысловые расхождения.
### Производительность:
- TTFT — время до первого токена.
- Время полного ответа.
- Скорость генерации (tokens/sec).
- Потребление RAM/VRAM.
- Ошибки, зависания и тайм-ауты.
И здесь я бы установил принципиальное правило:

RAMVI нельзя считать стабильным только потому, что он ответил на 100 вопросов так же, как Ollama.

Нужны и функциональные тесты движка, и качественное сравнение ответов. А если RAMVI отвечает правильно, но вдвое медленнее, это тоже важный результат, хотя и не обязательно блокирующий выпуск.

Eщё одна идея: после ручной проверки сохранить эти 100 вопросов как неизменяемый эталонный набор RAMVI Benchmark v1. Новые задачи добавлять в следующую версию набора, а не менять старую. Тогда можно будет сравнивать качество и производительность после каждого обновления.

И отдельно оставить небольшой набор новых, ранее не использованных вопросов, чтобы разработчики случайно не оптимизировали движок только под известный тест.
